# 第一篇　原理篇：先把这件事想明白

## 1.1 这套系统到底在做什么

一句话：**把"纸"变成"能查的数据库"，并且保留"这句话在纸上的第几页"这条线。**

传统做法是把 PDF 丢给 AI，AI 只能看到你贴给它的那几页；书一多就无从下手。这套系统的做法是：

1. 把每一份文献（扫描件、PDF、Word）**逐页**读成文字；
2. 在文字里保留**页码标记**（"这是原书第 137 页"）；
3. 把文字切成小块，每块算一个"语义向量"（一串数字，代表这段话的意思），全部存进一个数据库文件；
4. 你提问时，系统同时用两种方式找：**关键词**（字面匹配）和**向量**（意思相近），把两边结果合并排序，交给 AI 作答；
5. AI 回答时引用具体的块，因而能给出**文件名 + 页码**，你随时可以翻回纸本核对。

### 为什么必须保留页码

研究生写论文，最有价值的不是"AI 帮我找到这句话"，而是"**我能把这句话准确引到注释里，并且经得起审稿人问**"。
所以本系统的核心不是"搜索快不快"，而是**页码这条线从扫描页一路贯通到你的论文注释**。这条线一断，你得到的只是一堆"看起来对"的文本，没法引用。

### 三个零件

| 零件 | 通俗解释 | 本机实际情况 |
| --- | --- | --- |
| **Python** | 真正干活的程序：读 PDF、认字（OCR）、算向量、查数据库 | Python 3.14.7，装在 `C:\Python314\` |
| **DSH** | 指挥台：你在这里和 AI 对话，AI 去调用 Python 干活 | 版本 0.1.1-rc.2，浏览器访问 `http://127.0.0.1:3080` |
| **文献库** | 一个文件夹里的一个文件，装着全部文字、页码、向量 | `<DSH_ROOT>\example-project\.kb\kb.sqlite`（66.38 MB） |

三者关系：**你 → DSH（界面）→ AI（决定做什么）→ 工具（发起动作）→ Python 引擎（真正执行）→ kb.sqlite（数据落盘）**。

## 1.2 两种操作入口：你该用哪个

系统给了两条路去操作同一个数据库。**很多人搞混这两条路，结果以为"系统坏了"**——其实只是走错了门。

| | **对话工具**（推荐给不写代码的人） | **命令行脚本**（工具箱） |
| --- | --- | --- |
| 长什么样 | 在 DSH 里说"把新文献入库"，AI 就去调用 | 在 PowerShell 里敲 `python xxx.py` |
| 谁在用 | 你 | 你，或 AI 代你敲 |
| 典型任务 | 入库、检索、问答、统计、去重 | OCR、页码标定、引文定位、批量修数据 |
| 优点 | 不用记命令，AI 会挑参数 | 能力最全（工具只有 10 个，脚本有 90 多个） |
| 缺点 | 只覆盖常用功能 | 需要照着文档抄命令 |

**判断规则**：
- "我想查东西/想让新书进库" → **对话**；
- "我要处理扫描件、要算页码、要核引文" → **命令行脚本**；
- 拿不准 → 先问 AI："这件事该用哪个工具？"它知道。

> ✅ **`toolkit_*` 那 8 个工具已于 2026-09-16 修复**。此前它们全部报
> `output.render failed: userRender is not a function`——根因不是"DSH 版本不匹配"，而是**这个插件自己没给 `output` 提供 `render`**，而宿主的 `defineTool()` 会无条件调用 `output.render(...)`（新旧 DSH 版本都是这样写的，所以换版本也好不了）。
> 已给 8 个工具补齐 `render`（改的是我们自建的插件，不依赖上游）。**需重启 DSH 生效**；重启前仍可用命令行 `python <REPO>/tools\toolkit.py <命令>`。
>
> **另外，插件万一整体失效时的保底通道**：`kb_cli.py` 直接驱动知识库引擎，不经过插件——见 §3.13。

## 1.3 目录结构与命名规范

### 推荐的目录结构

```
<DSH_ROOT>\
├── _toolkit\                     ← 工具箱：90+ 个 Python 脚本 + 插件 + 索引
├── skill\                        ← 技能与文档工作区
│   ├── 文献库构建SOP.md
│   ├── 复刻手册_在另一台电脑复现文献库流程.md
│   ├── 本文件（文献库完全操作指南.md）
│   ├── 检查环境.ps1 / 启动DSH.ps1 / 迁移_改路径.py
│   └── .dsh\skills\literature-db-pipeline\SKILL.md    ← 让 AI 会做这件事的"技能"
└── example-project\               ← 研究工作区（名字可以随你取）
    ├── .kb\
    │   └── kb.sqlite             ← ★ 数据库本体（文档数 / 块数 / 向量数）
    ├── 01_文献\                   ← 把 PDF / Word / 扫描件都放这里
    ├── 05_文献数据库\              ← 题录、引文台账、索引等衍生数据
    └── topic-b\               ← 论文与专项材料
```

### 两条死规矩

1. **`.kb` 这个文件夹名不能改，里面的 `kb.sqlite` 也不能改名。** AI 的工具把这两个名字写死了，改了库就找不到了。
   **想让数据库有个好名字，就让 `.kb` 外面那层文件夹叫那个名字**——这正是工作区叫"example-project"的原因。
2. **数据库放在哪个工作区，决定了 AI 能不能自动找到它。** 规则是：AI 默认用「你打开会话的那个工作区」下面的 `.kb`。所以把库放在研究工作区根目录，以后在该工作区问话**不需要额外指定路径**。

### 文件命名规范（让下游脚本和人一眼认出）

| 文件名后缀 | 是什么 | 谁生成 |
| --- | --- | --- |
| `XXX.OCR.md` | OCR 逐页文字（带页标记、页眉/页下注标记） | `_ocr_pdf_to_md.py` |
| `XXX.OCR.layout.json` | 每页的版式参数（几栏、有没有页眉脚注） | `_ocr_layout.py` |
| `XXX.OCR.quality.md` | 质量报告：哪几页需要人工复核 | `_ocr_pdf_to_md.py` |
| `XXX.PAGES.md` | **入库用**：页标记＝**印刷页码**（`#### 第 N 页`） | `_ocr_md_to_pages.py` / `_docx_pages_to_md.py` |
| `XXX.full.md` | 正文＋脚注＋尾注全文 | `_docx_full_text.py` |
| `kb.sqlite.bak-日期-原因` | 数据库备份 | 护栏脚本自动生成 |

> ⚠️ **入库要入 `.PAGES.md`，不要直接入 `.OCR.md`**——除非该卷页码还没换算成印刷页码，而你能接受"库里的页码和纸本对不上"。

## 1.4 一条铁律：页码主线

**页码必须在"文本化阶段"就写进文字里**，不要等入库后再补。原因：数据库的分块器会把 `#### 第 N 页` 这类页标记**抽走**、存进 `chunks.section` 字段，于是：

- 检索结果里直接能看到"§第 137 页"；
- 可以用筛选条件精确定位"某卷某页"；
- 引文核对时能直接和纸本对照。

如果入库时没有页标记，后面想补就得**整库重灌**。这是本系统里最贵的一次错误。

# 第二篇　安装篇：从零把系统装起来

## 2.0 安装顺序（照这个顺序做，不要跳）

1. Python → 2. Node.js → 3. DSH → 4. kb-rag 插件＋Python 依赖 → 5. 其余插件 → 6. 打补丁 → 7. 搬工具与技能 → 8. 准备模型 → 9. 自检。

> **中途每完成一步都验证一次**。跳步装完再回头排错，会难十倍。

## 2.1 准备工作

### 硬件与系统

| 项目 | 要求 | 说明 |
| --- | --- | --- |
| 系统 | Windows 10 / 11 64 位 | 本机是 Windows 11 Home 10.0.26200 |
| 内存 | 建议 16 GB 以上 | 本机 32 GB；OCR 与向量计算吃内存 |
| 硬盘 | **至少 20 GB 空闲** | 模型约 1.2 GB（含重排序）；数据库与 OCR 产物增长很快 |
| 网络 | 首次安装需要 | 之后可完全离线运行 |

### 目录规划

**强烈建议保持 `<DSH_ROOT>\` 这个结构**。理由很实在：现有 90 多个脚本里，**大量路径是写死的**（例如工具箱里默认数据库位置就是 `<DSH_ROOT>\...\.kb\kb.sqlite`）。保持同样的目录名，这些脚本**开箱即用**；换成别的路径，就得批量改（有现成脚本，见 2.8 与第 6 篇）。

### 关于中文用户名

> ⚠️ Windows 用户名如果是中文，旧版安装脚本会报 `WinError 123`。新版（1.6.3 以上）已修复。**如果机器已装好且用户名是中文，不必重装系统**，直接继续；万一报错，见第 6 篇的对应条目。

## 2.2 安装 Python（最关键的一步）

### 下载

1. 浏览器打开 `python.org` → 顶部 `Downloads` → `Windows`；
2. 选择 **Python 3.14.x** 的 64 位安装包（文件名形如 `python-3.14.7-amd64.exe`）下载。
   > 为什么强调 3.14：本机验证过的版本是 3.14.7，且相关依赖（torch、sentence-transformers、PyMuPDF）在该版本下都能正常安装。**不要装 3.13 以下**，也不要装 32 位版本。

### 安装

1. 双击安装包；
2. **在第一个界面底部勾选 `Add python.exe to PATH`**；
   > ⚠️ 这一步是本篇最容易出错的地方。不勾，后面每一条 `python` 命令都会报"无法将 python 项识别为 cmdlet、函数、脚本文件或可运行程序的名称"。此时**不用卸载重装**，重新运行安装包 → 选 `Modify` → 把该选项勾上即可。
3. 点 `Install Now` → 等待 → `Close`。

### 验证

按 `Win + R`，输入 `powershell`，回车。在弹出的窗口里**复制粘贴**下面两行（逐行回车）：

```powershell
python --version
pip --version
```

✅ **成功的样子**：分别显示 `Python 3.14.7` 和 `pip 25.x`。
❌ 报"无法识别" → 回到上面第 2 条处理 PATH。

### 换成国内 pip 镜像（强烈建议）

Python 包默认从国外服务器下载，国内经常慢到超时。**一次性设好镜像**（在同一个 PowerShell 窗口执行）：

```powershell
python -m pip config set global.index-url https://pypi.tuna.tsinghua.edu.cn/simple
```

✅ **成功的样子**：提示 `Writing to ...pip.ini`。
以后所有 `pip install` 都会自动走清华镜像。

## 2.5 安装 kb-rag 插件（文献库的核心）

这是**整套系统的核心插件**，提供全部 10 个数据库工具。

### 方式对照（选一种即可）

| 方式 | 命令 | 适用 |
| --- | --- | --- |
| **① 一键安装器（推荐）** | `npx dsh-kb-rag-install` | 全新机器，一条命令搞定"插件＋Python 依赖＋模型" |
| ② 等价旧写法 | `npx --yes --package dsh-kb-rag -c "dsh-kb-rag-install --profile web"` | 方式①报 E404 时 |
| ③ 手动装包 | `dsh plugin --profile web add dsh-kb-rag` | 只装插件，Python 依赖另装 |
| ④ 插件市场 | GUI 里点安装 | 完全不想碰命令行 |

**推荐方式①**，在 PowerShell 里执行：

```powershell
npx dsh-kb-rag-install
```

它会依次做四件事：
1. 安装并激活插件；
2. 检查/安装 Python 依赖（`pymupdf`、`faiss-cpu`、`sentence-transformers`）；
3. 跑一次引擎自检（smoke test）；
4. （加 `--models` 时）预下载模型。

| 参数 | 作用 |
| --- | --- |
| `--profile web` | 装到 web 这个配置档（本机就是它） |
| `--models` | 顺便把模型也下载好（约 1.2 GB，含重排序模型） |
| `--mirror <网址>` | 用国内 pip 镜像加速 |
| `--dry-run` | **只演练不改动**，第一次装建议先跑一遍看流程 |

✅ **成功的样子**：最后打印依赖齐全、引擎自检通过、插件已激活。
❌ 报 `npm error code E404` → 执行 `npm cache clean --force` 后重试。

> ⚠️ **首次启动会检查依赖但不自动安装**。插件会把你缺的包和对应的 `pip install` 命令打印到日志里。如果你希望它自动装，可设环境变量 `KB_AUTO_PIP=1`（装之前建议先看清它要装什么）。

## 2.7 打一个关键补丁（不打，kb-rag 会静默失效）

> **这一条是整篇安装篇里最容易被忽略、后果最严重的一步。**

背景：`dsh-win32` 在 Windows 上会**停用**平台自带的 `subprocess` 服务行，改用自己的一条替代行；但那条替代行位于另一个补丁层，**所有插件都取不到这个服务**。实测证据（宿主日志原文）：

```
subprocess service unavailable; tools not registered
```

也就是说：**kb-rag 会在启动阶段直接放弃注册全部 10 个工具**——你在对话里根本看不到它们，而且不会报错。

**解决办法**：编辑（不存在就新建）文件

```
C:\Users\<你的用户名>\.dsh\profiles\web\cordis.patch.yml
```

把下面两段**整段**追加进去（若文件已有内容，直接追加到末尾）：


# 第三篇　数据库功能篇

## 3.1 数据库里到底存了什么

### 四张表

数据库是一个标准的 SQLite 文件（`kb.sqlite`），里面就四张表。**理解这四张表，你就能自己判断任何异常**。

```sql
docs    —— 一篇文献一行：文件在哪、标题、作者、年份、刊物、DOI、内容指纹、块数
chunks  —— 一个"块"一行：属于哪篇文献、章节名、权重、顺序号、正文、段落区间、页码区间
vecs    —— 一个块一行：这个块的向量（一串数字，代表语义）
cache   —— 检索缓存：同一个问题不重复计算
```

**字段详解**（本机实测的 schema）：

| 表 | 字段 | 含义 | 本机填充率 |
| --- | --- | --- | --- |
| `docs` | `path` | 文件绝对路径（**换电脑必须改的就是它**） | 100% |
| | `title` / `authors` / `year` / `journal` / `doi` | 题录信息（**由程序自动猜出来的，必须核实**） | 100% / 91.2% / 88.6% / 74.6% / **9.6%** |
| | `sha256` | 内容指纹，用来跳过没变的文件、拦下重复文件 | 100% |
| | `chunk_count` | 这篇被切成了多少块（**用来校验数据一致性**） | 100% |
| | `indexed_with` | 哪一版程序写的（用于识别"陈旧数据"） | 100% |
| | `zotero_key` | 来自 Zotero 时的条目编号 | 0% |
| `chunks` | `section` | 章节名；**页标记会被抽到这里**（形如"第 137 页"） | 100% |
| | `weight` | 检索权重；参考文献固定为 0（**0 = 不参与检索**） | 100% |
| | `seq` | 在这篇里的顺序号 | 100% |
| | `text` | 正文 | 100% |
| | `para_start` / `para_end` | 段落区间 | 100% |
| | `page_start` / `page_end` | **纸本页码区间**——引文能回查纸本，靠的就是它 | **97.0%** |

> **为什么 `doi` 只有 9.6%？** 因为多数中文期刊 PDF 内页里没有印 DOI，程序又**不允许编造**，只能留空。这是正常状态，不是故障。
> **为什么 `page_start` 是 97% 而不是 100%？** 剩下的 3% 是"确实没有印刷页码"的内容（卷首说明、题记、登记表一类）。系统**宁可留空也不猜**——这是设计选择。

### 页码是怎么进到库里的

三条来源，最终统一成**一个口径：印刷页码**。

| 来源 | 例子 | 换算 |
| --- | --- | --- |
| OCR 出来的页序 | "这是扫描文件的第 17 张" | 需要加偏移量（本机三卷分别是 +7、+7、+13） |
| Word 的页眉 | 页眉印着"137" | 直接就是印刷页码 |
| 扫描页自己的页眉 | 同上 | 直接就是印刷页码 |

**为什么必须统一**：三种来源混在一个库里，同一批引文在不同卷上按不同基准标注，**看起来都对，实际全错**。

## 3.2 入库：`kb_ingest`

这是最常用的功能。在对话里说"把 `01_文献` 里的文件入库"，AI 就会调用它。

### 参数逐个讲

| 参数 | 作用 | 什么时候用 |
| --- | --- | --- |
| `paths` | 要入库的文件或文件夹（**支持递归**，文件夹里的子目录都会扫） | 每次都用 |
| `kb_root` | 指定数据库位置 | **只有在会话工作区不是数据库所在目录时才需要** |
| `force` | 强制重新解析（即使文件没变） | 换了新版本程序、想补上新的解析数据（如页码锚点、上标引文）时 |
| `metadata_only` | **只刷新题录**（标题/作者/年份/刊物/DOI），不重新切块、不重算向量 | 批量修正题录时。速度极快，**约 90 毫秒/篇** |
| `rebuild` | 按库里记录的原路径把**每篇**都重新解析一遍 | 程序大版本升级后、或改了切块规则后 |
| `paths` 省略 + `rebuild=true` | 原地重灌库里全部文档 | 不需要再指定路径，最省事 |

### 三种"重新处理"的区别（最容易搞混）

| 你想要的效果 | 用哪个参数 | 会重新切块吗 | 会重算向量吗 | 速度 |
| --- | --- | --- | --- | --- |
| 只修正作者/年份/刊物 | `metadata_only=true` | 否 | 否 | 极快（90 ms/篇） |
| 重新解析（含页码锚点等新数据） | `rebuild=true` | **是** | **是** | 慢（按块数算） |
| 某个文件改了内容后更新 | 直接重新 `kb_ingest` 该文件 | 是 | 是 | 中 |

### 增量、去重与后台任务

- **增量**：靠内容指纹（`sha256`）判断——文件内容没变就**跳过**。所以"把整个文件夹再入一次"是安全的，不会重复。
- **去重**：同一个文件放在两个文件夹里，第二次会被识别为重复并跳过。
- **后台任务**：待入库文件**超过 25 个**（阈值 `KB_ASYNC_THRESHOLD`）时，任务会自动转后台，返回一个 `job_id`。此时用 `kb_status` 轮询进度，**不用担心对话超时把任务打断**。

### 什么该入库、什么不该

| 该入库 | 不该入库 |
| --- | --- |
| 书籍、期刊论文、档案的正文 | 纯元数据页（如下载站导出的说明页）——会污染检索 |
| 带页码标记的 `.PAGES.md` | 没有页码、且你无法接受这一点的 `.OCR.md` |
| 你自己的读书笔记（如果希望和文献一起被检索到） | 数据库自己的导出文件（`literature_db*.json`）——会自我循环 |

### 验收标准

✅ **成功的样子**：返回 `added / updated / skipped / errors` 四类计数，且**错误为 0**。
❌ 有 `errors` → 逐个看原因（常见是 PDF 加密、文件损坏、路径含特殊字符）。

## 3.3 看进度：`kb_status`

`kb_ingest` 返回 `job_id` 后（大批量时），用 `kb_status(job_id="...")` 轮询：

- 运行中 → 显示已处理篇数、错误数、已生成块数；
- 完成 → 显示总数与最近 20 个文件；
- 出错 → 说明原因。

> 经验值：**一批 2000 块左右的入库，实测约 4 分钟**（本机 2,121 块 / 239.6 秒）。你可以据此估算。

## 3.4 检索：`kb_search`

系统的核心功能。**同样的查询词，换个模式，结果可能天差地别**——所以下面这张表要读懂。

### 参数

| 参数 | 可选值 | 说明 |
| --- | --- | --- |
| `query` | 文本 | **建议写英文术语串**（原因见 3.4.3） |
| `mode` | `hybrid`（默认）/ `keyword` / `vector` | 用哪种方式找 |
| `depth` | `quick` / `deep` | 轻量还是全链路 |
| `top_k` | 数字 | 返回几条 |
| `filters` | 见下 | 元数据筛选 |
| `rerank` | 真/假 | 是否启用重排序模型 |
| `related` | 真/假 | 是否附带"相关文献"推荐 |
| `snippet` | 数字 | 每条显示多少字 |
| `strict` | 真/假 | 严格模式：只依据检索到的证据 |
| `kb_root` | 路径 | 数据库位置 |

### 3.4.1 三种模式怎么选（最重要的一张表）

| 模式 | 原理 | 什么时候用 | 实测表现 |
| --- | --- | --- | --- |
| `keyword` | 字面匹配（BM25，支持中文二字切分） | **要核对逐字引文**（"这句话原文到底怎么写的"） | 一条 23 字的原句，**Top-1 精确命中** |
| `vector` | 语义相似（向量距离） | 换个说法也能找到 | 精确匹配差，模糊匹配好 |
| `hybrid`（默认） | 两种结果融合（RRF） | **概念性查找**、不确定原文措辞时 | 同一句原句 hybrid 进不了前 3 |

> ⚠️ **这条反直觉但很重要**：融合排序会把**精确匹配摊薄**。所以——
> **逐字核对引文，一定用 `keyword`；找概念，用默认的 `hybrid`。**
> 实测证据：同一条 23 字原句，keyword 模式 Top-1 命中，hybrid 与 vector 都进不了前 3。

### 3.4.2 `filters` 怎么用

`filters` 是**元数据筛选**，可以单独用，也可以组合：

| 字段 | 例子 | 说明 |
| --- | --- | --- |
| `title` | `"第5卷"` | 标题包含 |
| `section` | `"第 294 页"` | **章节名包含**——因为页标记被抽成了章节名，所以这条能**精确定位到某卷某页**（实测 55 毫秒返回） |
| `authors` | `"<作者名>"` | 作者包含 |
| `journal` | `"文史哲"` | 刊物包含 |
| `year` | `2021` 或 `">=2018"` | 年份，支持比较式 |
| `kind` | `"pdf"` / `"md"` | 文件类型 |

> ⚠️ **把限定条件放进 `filters`，不要塞进 `query`**。塞进查询词里的"2021年""某人名"，会占用关键词通道，反而降低正文匹配效果。

### 3.4.3 查询词怎么写（决定检索质量的头号因素）

**引擎不会替你翻译、不会替你改写查询**——你给什么词，它就按什么词找。所以查询词的语言必须和库内正文的语言对得上。

- **写成英文术语串**，不要写整句中文问句；
- **3–12 个词**，结构建议"材料/主题 ＋ 方法/路径 ＋ 性质/论证"；
- 中文库就写中文术语串；**只有当库里确实有中文文献、你要找的是它们时**，才用中文查询。

举例（本机实测有效）：`Liang Shuming rural reconstruction cultural conservatism`。
反例：`示例人物的乡村建设思想是怎么形成的？`（整句问句，关键词通道基本空转）。

### 3.4.4 `quick` 与 `deep` 的区别

| | `quick` | `deep` |
| --- | --- | --- |
| 做什么 | 混合检索后直接返回 | 额外做：重排序、引文关联、相关文献推荐 |
| 速度 | 快 | 慢一些 |
| 适合 | 查个具体事实 | 做领域调研、综述 |

### 3.4.5 怎么读检索结果

每条结果应包含：**标题 / 作者 / 年份 / 刊物 / DOI / 章节（含页码）/ 片段正文**。

- **有 DOI** → 可以直接点开原文链接；
- **没有 DOI** → 会给文件名，且应带上**完整磁盘路径**（这样你能直接打开）；
- **`§第 N 页`** → 这是**纸本页码**，可以直接写进论文注释。

> ⚠️ **如果路径点不开**，说明库内路径是旧电脑的——做一次路径迁移（见第 6 篇）。

## 3.5 问答：`kb_rag`

与 `kb_search` 的区别：`kb_search` 只**给你证据**，`kb_rag` 是**让 AI 拿着证据作答**，并给每个事实标注引用编号。

| 参数 | 说明 |
| --- | --- |
| `query` | 同 3.4.3 的写法建议 |
| `depth` | `deep`（默认，展开论述）/ `quick`（只给答案，不展开） |
| `top_k` | 证据条数（quick 默认 2 / deep 默认 3，上限 10） |
| `strict` | **严格模式**：只准依据库内证据回答，禁止补充库外知识 |
| `filters` / `related` / `rerank` | 同 `kb_search` |

**引用格式**（系统约定）：
- 有 DOI → `[作者, 年份, 刊物](https://doi/DOI)`（可点击）；
- 无 DOI → `[作者, 年份, 文件名]`。

> **写论文时建议开 `strict=true`**：宁可让 AI 说"库内资料不足"，也不要它用库外的常识补齐——那正是审稿人抓的地方。

## 3.6 检索范围：`kb_scope`

设置/查看三个开关：

| 开关 | 可选值 | 含义 |
| --- | --- | --- |
| `scope` | `kb` / `both` / `web` | 只用本地库 / 本地库＋联网 / 只联网 |
| `depth` | `quick` / `deep` | 默认检索深度 |
| `strict` | 真/假 | 默认是否严格模式 |

**建议**：正式写论文期间设为 `kb` + `strict: true`，避免模型把网络内容混进你的引证。

## 3.7 体检：`kb_stats`

一眼看清库的健康状况：

- 文档数 / 块数 / 向量数；
- 最近入库的文档列表；
- **`stale_docs`**：用**旧版程序**写入的文档。这类文档**增量入库永远不会再碰它**（因为内容没变），所以需要你主动用 `metadata_only` 或 `rebuild` 刷新。

> ⚠️ **默认路径陷阱**：`kb_stats` 不给 `kb_root` 时，查的是**当前会话工作区**下的 `.kb`。跨工作区查库**必须显式传绝对路径**，否则会显示"知识库为空"，让你误以为数据丢了。

## 3.8 采集文献：`kb_fetch` 与 `kb_zotero`

### `kb_fetch`——按 DOI / arXiv 编号自动下载 PDF

| 参数 | 说明 |
| --- | --- |
| `identifiers` | DOI 或 arXiv 编号列表，如 `10.1038/xxxxx`、`arXiv:2401.00001` |
| `target_dir` | 下载到哪（默认 `~/.kb-rag/downloads`） |

**下载顺序**（设计如此，逐级退让）：arXiv 直连 → **出版商正式版**（在校内网/机构订阅网络下能直接拿到订阅版）→ 落地页里的 PDF 链接 → 开放获取兜底（Unpaywall / Crossref）。
**它不做的事**：不绕过付费墙、不访问 Sci-Hub、不伪造凭据。

> 下载完**不会自动进库**，需要你再 `kb_ingest` 一次。

### `kb_zotero`——把 Zotero 文献库批量搬进来

| 参数 | 说明 |
| --- | --- |
| `zotero_db` | `zotero.sqlite` 路径（不给则自动找 `~/Zotero` 等常见位置） |
| `dry_run` | **试运行**：只列候选、不写入。**第一次务必先跑这个** |
| `limit` | 最多搬几篇 |
| `force` | 强制重新解析已入库的附件 |

行为：读 Zotero 数据库 → 找出**带 PDF 附件**的条目 → 取题录（标题/作者/年份/刊物/DOI）→ 逐篇入库；已入库的自动跳过，附件文件缺失的标记为 `missing` 并跳过（**不会尝试下载**）。

## 3.9 清理：`kb_dedup` 与 `kb_clear`

| 工具 | 作用 | 风险 |
| --- | --- | --- |
| `kb_dedup` | 删除内容重复的文档（**保留最早入库的那一篇**），同步清掉它的块与向量 | 低（反复执行安全） |
| `kb_clear` | **清空全部文献与索引** | **极高——不可恢复** |

> ⚠️ `kb_clear` **必须显式传 `confirm: true`** 才执行（否则拒绝）。执行前请务必手工复制一份 `kb.sqlite` 出去。**在意图明确之前，不要使用这个功能。**

## 3.10 `kb_root` 规则与"空壳陷阱"

### 规则

`kb_root` 指的是**直接存放 `kb.sqlite` 的那个文件夹**，也就是 `.kb` 本身。

- **不给** → 用「当前会话工作区」下的 `.kb`；
- **给了** → 用你给的那个目录（它下面必须有 `kb.sqlite`）。

**所以最佳实践是**：把库放在你常开会话的工作区根目录下，**什么都不用传**。

### 空壳陷阱（务必知道）

**引擎在找不到数据库时会自动新建一个空库，而且不报错。** 后果是：

- 你以为在用真库，实际查的是一个空库 → 显示"知识库为空"；
- 或者你在错误的目录下反复操作，慢慢积攒出好几个空壳文件。

**识别方法**：真库有几十 MB 以上；**空壳只有几十 KB**。
**预防方法**：`检查环境.ps1` 会自动把空壳标出来（本机就曾有过 3 个空壳：`skill\.kb\`、工作区根下的游离 `kb.sqlite`、以及 `.kb\` 里的一个）。

## 3.11 什么时候必须直接改数据库

有些维护动作工具做不到（例如：批量回填页码字段、修正抓错的作者名、清理悬空记录）。这时要**用 SQL 直接改库**。**必须守三条规矩**：

1. **先备份**：改之前把 `kb.sqlite` 复制一份，命名 `kb.sqlite.bak-日期-原因`；
2. **先试运行**：脚本默认应当是"只看不改"，确认输出无误再加 `--apply`；
3. **写完立刻核对计数**：文档数、块数、带页码块数——**不增反减就是出事了，立刻回滚**。

系统里有一个**写库护栏** `_kb_guard.py`，把上面三条做成了自动动作（备份 → 范围断言 → 单事务 → 写后校验）。

✅ **验证护栏可用**：

```powershell
python -B <REPO>/tools\_kb_guard.py --selftest
```

本机实测**7 项全部通过**，其中一项专门防历史事故——"把页码误写进块 ID 列"。

> **真实教训**：曾经因为 SQL 参数顺序写反（`SET page_start=?, page_end=? WHERE id=?` 传成了 `(id, 页码1, 页码2)`），导致 `WHERE id = 页码` **从未命中**。所幸该次误写没有污染数据；若命中，就会**静默写错列**——写库前不做断言，这类错误极难发现。

## 3.12 检索不到东西？按这 8 步排查

| 步骤 | 检查什么 | 怎么查 |
| --- | --- | --- |
| 1 | **库对不对** | `kb_stats`，看文档数是不是你要的那个库；注意空壳陷阱 |
| 2 | **文件入没入库** | 用文件名或标题在结果里找；或 `kb_coverage_vs_files.py` 对比磁盘与库 |
| 3 | **查询词语言对不对** | 库内是中文就写中文术语串，别用整句问句 |
| 4 | **模式对不对** | 逐字核对换 `keyword` 再试一次 |
| 5 | **筛选条件是否过严** | 去掉 `filters` 再试 |
| 6 | **是不是 OCR 质量问题** | 用 `_kb_find_text.py "某句原文"` 看这句话是否在库里、落在哪一块 |
| 7 | **是不是页码没进库** | 看结果的 `section` 是不是"第 N 页"；不是就说明入库用的是没页码的版本 |
| 8 | **是不是双栏/异体字问题** | 双栏按行读取会左右交错；旧 OCR 还会把"示例人物"认成"梁漱滇"一类的异体 |

## 3.13 保底通道：`kb_cli.py`（插件失效时也能用）

知识库能力其实由本机一个 Python 引擎（`kb_engine.py`）提供，**DSH 插件只是它的外壳**。`kb_cli.py` 绕开插件、直接按引擎协议通信——**插件整体失效时（例如将来升级 DSH 导致工具注册不上），入库与检索依然可用**。

```powershell
cd <REPO>/tools

# 统计
python -B kb_cli.py --kb-root "<DSH_ROOT>\example-project\.kb" stats

# 入库（首次在某位置建库要加 --create，避免"以为在用真库、其实在建空库"）
python -B kb_cli.py --kb-root <库目录> ingest "D:\资料\新文献" 
python -B kb_cli.py --kb-root <库目录> ingest "D:\资料\新文献" --create

# 检索（逐字核对引文用 keyword；概念查找用默认 hybrid）
python -B kb_cli.py --kb-root <库目录> search "Liang Shuming rural reconstruction" --mode keyword --top-k 5
python -B kb_cli.py --kb-root <库目录> search "文化失调" --section "第 294 页"

# 取证据（供人据此作答）
python -B kb_cli.py --kb-root <库目录> rag "示例人物如何论证乡村建设"
```

**库位置（`kb_root`）解析顺序**：`--kb-root` 参数 → 环境变量 `KB_ROOT` → 当前目录下的 `.kb` → 都没有则报错退出（**绝不擅自新建**）。
一次性设好省得每次传：`setx KB_ROOT "<DSH_ROOT>\example-project\.kb"`（新开窗口生效）。

**引擎位置**自动从 `~\.dsh\profiles\*\node_modules\dsh-kb-rag\kb_engine.py` 找；可用 `--engine` 指定。

**两条实测行为**（都不算故障，但会让人误判）：
1. **过短的文件入库后是 0 块**，因此检索不到——引擎对过短文件不建索引。命令会明确提示。
2. **md 文件的标题会保留开头的 `#`**（如 `# 示例文集 第5卷…`）——引擎取首行作标题时的既有行为。

# 第四篇　模型篇：每一处用到 AI 模型的地方

## 4.1 全景：这套系统一共用了 5 个模型

| 模型 | 体积 | 干什么 | 什么时候加载 | 缺了会怎样 |
| --- | --- | --- | --- | --- |
| `BAAI/bge-small-zh-v1.5` | 92–95 MB | **嵌入**：把文字变成向量，让"意思相近"能被找到 | 第一次检索/入库时，由常驻引擎加载（实测约 5.7 秒） | 检索退化成纯关键词，语义查找失效 |
| `BAAI/bge-reranker-base` | **约 1.1 GB** | **重排序**：把粗排出来的 20 条重新精排成 3 条 | 深度检索时 | 自动降级（见 4.3） |
| `BAAI/bge-large-en-v1.5` | 约 1.3 GB | 重排序的**备胎**（交叉编码器不可用时用它） | 同上 | 同上 |
| RapidOCR 检测模型 `ch_PP-OCRv3_det` | 2.3 MB | OCR 第一步：找出图里哪儿有字 | 每次 OCR | 扫描件无法入库 |
| RapidOCR 识别模型 `ch_PP-OCRv3_rec` | 10.2 MB | OCR 第二步：把框里的字认出来 | 每次 OCR | 同上 |
| （附）RapidOCR 方向模型 `ch_ppocr_mobile_v2.0_cls` | 0.6 MB | 判断这行字是不是倒的 | 每次 OCR | 倒置文字可能认错 |

> **记忆要点**：**嵌入模型决定"能不能找到"，重排序模型决定"排得准不准"，OCR 模型决定"扫描件能不能变成字"。**
> 三个 OCR 模型已打包在 Python 包里，**不联网也能用**；两个检索模型需要单独下载。

## 4.2 嵌入模型：`bge-small-zh-v1.5`

### 它做什么

把一段文字变成 512 个数字（**实测 512 维**）。意思相近的两段话，这串数字在空间里的距离就小。于是"用户换个说法提问"也能找到原文——这是关键词匹配做不到的。

### 为什么选"small"而不是更大的模型

- **快**：92 MB、512 维，检索快、内存占用小；
- **中文友好**：`-zh` 表示针对中文语料训练；
- **够用**：本系统的检索质量瓶颈通常**不在嵌入模型**，而在文本质量（OCR 准不准、页码对不对）。

> **本机的核心判断**：数据库的可靠性**不取决于向量模型有多强**，而取决于"页码这条线"有没有贯通。换更大的模型通常不会解决你实际遇到的问题。

### 换嵌入模型会付出什么代价

**必须整库重灌**，理由是：

1. 向量之间只有**同一个模型产生的**才可比——新旧混在一个库里，距离毫无意义；
2. 库里**没有记录"这批向量是哪个模型算的"**（`docs` 表只有"哪一版程序写的" `indexed_with`，没有模型字段），所以系统**不会提醒你**换了模型，只能靠你自己记得。

**操作步骤**：

```powershell
# ① 设环境变量，指定新模型
$env:KB_EMBED_MODEL = "BAAI/bge-large-zh-v1.5"

# ② 重启 DSH（让引擎用新模型）
powershell -ExecutionPolicy Bypass -File <DSH_WORKSPACE>\启动DSH.ps1

# ③ 整库重灌（重建分块并重算向量）
#    在对话里让 AI 执行：kb_ingest(rebuild=true)
```

> ⚠️ 重灌前**必须备份**。重灌会重写全部块与向量，中途失败可能留下半新半旧的库。
> **建议**：除非有明确理由，**不要换嵌入模型**。默认的 bge-small-zh-v1.5 对本系统的实际瓶颈（OCR 与页码）没有影响。

## 4.3 重排序模型：`bge-reranker-base`

### 它做什么

粗排阶段（BM25 ＋ 向量）先捞出**约 20 条**候选，重排序模型再用一个更精细的方式把这 20 条**重新打分，取前 3 条**。它比向量检索准，但慢得多，所以只用在最后一步。

### 本机的实际情况（诚实说明）

**本机没有下载这个模型**——因为它有 **1.1 GB**。后果是：**深度检索的"重排序"环节会自动降级**。

引擎的降级链是：

```
bge-reranker-base（交叉编码器，最准）
    ↓ 拿不到
bge-large-en-biencoder（备胎，次之）
    ↓ 也拿不到
直接用混合检索的排序（quick 模式的排序）
```

✅ **怎么判断现在用的是哪一档**：看检索返回的耗时与排序质量。如果深度检索和快速检索的结果几乎一样，说明重排序**没有真正生效**。
❌ 也可看宿主日志里有没有"请求 `bge-reranker-base` 失败"的记录。

### 想要更好的排序怎么办

```powershell
# 用国内镜像下载（1.1 GB，请留足时间）
$env:HF_ENDPOINT = "https://hf-mirror.com"
npx dsh-kb-rag-install --models
```

下载完成后，`检查环境.ps1` 的"模型缓存"一节会显示 `OK bge-reranker-base`。

> **要不要装？** 看你的用法：
> · 只是"找得到、能引用" → **不用装**，省 1.1 GB 和加载时间；
> · 要做综述、要"最相关的那 3 条" → **值得装**。

## 4.4 OCR 模型与扫描件处理

### 认字能力的天花板在哪

RapidOCR 用的是 PP-OCRv3 系列（中文），对**印刷体横排**效果很好，对以下情况会出错：

| 情况 | 表现 | 对策 |
| --- | --- | --- |
| 竖排古籍 | 阅读顺序错乱 | 系统只搭了框架，**未在真实竖排件上验证**（已知短板） |
| 双栏排版 | 左右栏交错成一句 | 用**新版式感知 OCR**（已内置栏数判定：先左后右） |
| 页眉页脚 | 混进正文 | 系统的 OCR 会把页眉、页下注单独标记出来 |
| 生僻字/异体字 | "示例人物"→"梁漱滇" | 无法根治；**引用时务必逐字核对** |
| 插图/公式页 | 只有零星字符 | 在质量报告里会被列为"过短页" |

### 扫描件的正确处理流程

```powershell
cd <REPO>/tools

# ① 先体检：页数、有没有文字层（决定要不要 OCR）
python -B _pdf_scan_check.py "某书.pdf"

# ② 版式预检：几栏？有没有页眉脚注？（抽样 6 页，很快）
python -B _ocr_layout.py "某书.pdf" --pages 6

# ③ 正式 OCR：产出 .OCR.md + .layout.json + .quality.md
python -B _ocr_pdf_to_md.py "某书.pdf" --dpi 200

# ④ 看质量报告，挑出需要人工复核的页
#    打开 "某书.OCR.quality.md"
```

### 参数怎么选

| 参数 | 建议 | 理由 |
| --- | --- | --- |
| `--dpi 200` | 常规印刷体用 200 | 更高更准但更慢；模糊小字可用 300 |
| `--pages N` | 只做预检时用 | 抽样看版式，不必跑全本 |
| `--resume` | **长任务中断后续跑** | 几千页的书一定要用这个思路 |
| `--no-probe` | 跳过预检直接 OCR | 已确认版式时用 |
| `--profile` | 指定版式档 | 版式固定的一批书可复用同一档 |

### 速度与心理预期

**实测约 5 页/分钟**（几百页的卷是「数十分钟到数小时」的量级）。
**这意味着**：一本 700 页的书要 **2–3 小时**。请**放在空闲时间跑**（例如过夜），不要一直盯着。

## 4.6 联网与离线：为什么必须设离线

### 问题的由来（本机真实故障）

某些网络环境下，本机到 HuggingFace（Fastly / Cloudflare）的 **TCP 连接会一直挂着**（不是立刻失败，而是"永远在连"）。后果非常典型：

1. 引擎尝试下载一个**未缓存**的模型（如重排序模型）；
2. 连接悬挂 → 引擎**卡在那里**；
3. 因为引擎是**串行**处理请求的，整个进程被拖住；
4. 你看到的现象是：**检索永远不返回**。

这不是"网络慢"，而是**卡死**。设成离线之后，引擎会立刻发现"本地没这个模型"，**快速降级**，检索照常返回。

### 怎么设

```powershell
$env:HF_HUB_OFFLINE = "1"
$env:TRANSFORMERS_OFFLINE = "1"
```

**建议写进启动脚本**（`启动DSH.ps1` 已经做了），这样**每次重启都不会忘**。

✅ **验证是否生效**：`检查环境.ps1` 会检查这两个变量；也可在任何子进程里直接看：

```powershell
echo $env:HF_HUB_OFFLINE
```

✅ **成功的样子**：输出 `1`。
❌ 输出为空 → 说明你是用别的方式（或直接 `dsh web`）启动的，那层保护没生效。

> ⚠️ **本机曾经就是这样丢过保护的**：某次重启没有通过启动脚本执行，日志不再落盘、离线变量也没设上。所以：**重启一律用 `启动DSH.ps1`**。

## 4.7 性能基准与调优

### 实测基准（本机数据，可作参照）

| 操作 | 实测 | 说明 |
| --- | --- | --- |
| 检索（快速，冷启动） | **34.3 秒** | 含嵌入模型加载；之后同查询走缓存 |
| 检索（深度，缓存命中） | **435 毫秒** | 同一查询 + 筛选条件完全相同时不重算 |
| 入库 | **2,121 块 / 239.6 秒**（约 8.9 块/秒） | 1000 页的书约 5–15 分钟 |
| 题录刷新 | **约 90 毫秒/篇** | `metadata_only=true` |
| 嵌入模型首次加载 | **约 5.7 秒** | 常驻引擎只加载一次 |
| OCR | **约 5 页/分钟** | 700 页约 2–3 小时 |
| 精确取某页 | **55 毫秒** | `filters.section` 直达 |
| 库体规模 | 文档百余篇 / 万块级 | 约几 KB/块 |

### 慢在哪，怎么判断

| 症状 | 最可能的原因 | 处理 |
| --- | --- | --- |
| 第一次检索要几十秒 | 模型正在加载（一次性） | 正常；常驻引擎会保持 |
| 每次都慢 | 每次都在重启引擎 | 检查是不是每次都在重启 DSH |
| 检索卡住不返回 | **联网下载模型被挂住** | 设 4.6 的离线变量 |
| 入库慢 | 文件多、扫描件多 | 转后台任务跑，别守在对话里 |
| 检索结果少 | 文本质量差（OCR 错字） | 修文本，而不是换模型 |
| 磁盘增长快 | OCR 中间产物 + 备份 | 定期清理；备份设保留上限 |

## 5.1 十二步总览

> 每步都给了**命令**与**验收标准**。更详细的规范（失败模式、工具分级）见 `文献库构建SOP.md`。

| # | 步骤 | 命令 / 入口 | 验收标准 |
| --- | --- | --- | --- |
| 1 | **素材体检** | `python -B _pdf_scan_check.py "书.pdf"` | 页数已知；**无文字层的单独列出** |
| 2 | **版式预检** | `python -B _ocr_layout.py "书.pdf" --pages 6` | 栏数判定有依据；低置信页有清单 |
| 3 | **文本化**（三选一） | 扫描件→`_ocr_pdf_to_md.py`；Word→`_docx_pages_to_md.py`；已有 OCR→`_ocr_md_to_pages.py` | 页标记连续、且等于源文件页数 |
| 4 | **页码标定** | `python -B _page_number.py "书.OCR.md"` | 偏移量**自证**：命中页印着推算出的页码，且差值**成片**而非散点 |
| 5 | **口径统一** | `python -B _ocr_md_to_pages.py` | 全库页标记＝**印刷页码**；换算前后引文页码逐条一致 |
| 6 | **入库** | 对话里 `kb_ingest` | 条数明确；**块数＝向量数**；错误 0 |
| 7 | **结构核查** | `python -B _kb_audit2.py` | 悬空文档 0；`chunk_count` 零不一致；无重复指纹 |
| 8 | **检索验证** | 对话里 `kb_search`（`mode=keyword`） | 逐字原句能 Top-1 命中；`filters.section` 能定位某页 |
| 9 | **引文定位** | `python -B _cite_page_candidates.py` | 每条候选都有**页内原文**印证 |
| 10 | **交叉验证** | `python -B _crosscheck_pages.py` | **两条独立路径**的页码一致才允许写进论文 |
| 11 | **校勘与回填** | `python -B _quote_collation.py` / `_insert_page_numbers.py --apply` | 差异逐条列出；未核实的标"待回查纸本" |
| 12 | **治理** | `_kb_guard.py` 护栏 + `_kb_dedup` + 备份 | 备份存在；写后计数不增反减即报警 |

**最容易被跳过、但后果最重的两步**：第 5 步（口径统一）和第 10 步（交叉验证）。
跳过它们，你会得到一批"看起来都合理、但互相矛盾"的页码。

## 5.2 第一次使用的完整演练（照着做，约 30 分钟）

这一节假设你**完全没做过**，从打开电脑开始一步步走完。**每一步都写清"你会看到什么"**——如果你看到的和写的不一样，就停下来查第六篇。

### 准备

找 **3 个 PDF** 放进文件夹（先别放太多，第一次练手用）：一个普通的文字版论文 PDF、一个扫描件书页、一个 Word 文档。都放进 `<DSH_ROOT>\example-project\01_文献\`。

✅ **成功的样子**：
```
<DSH_ROOT>\example-project\01_文献\
    ├── 测试论文.pdf
    ├── 测试扫描页.pdf
    └── 测试文稿.docx
```

### 第 1 步：体检素材（命令行）

按 `Win + R` 输入 `powershell` 回车，粘贴：

```powershell
cd <REPO>/tools
python -B _pdf_scan_check.py "<DSH_ROOT>\example-project\01_文献\测试论文.pdf"
python -B _pdf_scan_check.py "<DSH_ROOT>\example-project\01_文献\测试扫描页.pdf"
```

**你会看到**：每个文件的页数，以及"有没有文字层"的判定。

| 判定结果 | 含义 | 下一步 |
| --- | --- | --- |
| 有文字层 | PDF 里本来就带文字 | 可以直接入库 |
| **无文字层**（`no_text_layer`） | 是图片扫描件，必须先 OCR | 走第 2、3 步 |
| 提取出来的字很少（几十个字） | 也是扫描件 | 同上 |

> **这一步的意义**：不体检就入库，扫描件会以"只有几十个字"的状态进库，你搜不到内容，还以为是系统坏了。

### 第 2 步：看版式（只针对扫描件）

```powershell
python -B _ocr_layout.py "<DSH_ROOT>\example-project\01_文献\测试扫描页.pdf" --pages 6
```

**你会看到**：判定出的栏数（单栏/双栏）、有没有页眉、有没有页下注、有没有警告。

> **为什么先看这个**：双栏排版如果不做处理，OCR 会把左右两栏按行交错读，得到"梁漱汉先生是中国20世纪的思想大家之一。人／驭的无政府共产主义"这样前后不通的句子——**逐字引文将永远搜不到**。

### 第 3 步：OCR

```powershell
python -B _ocr_pdf_to_md.py "<DSH_ROOT>\example-project\01_文献\测试扫描页.pdf" --dpi 200
```

**你会看到**：进度逐页刷新。跑完后目录里多出三个文件：

```
测试扫描页.OCR.md            ← 逐页文字（带页标记）
测试扫描页.OCR.layout.json   ← 每页版式参数
测试扫描页.OCR.quality.md    ← 质量报告：哪几页需要人工看
```

✅ **成功的样子**：用记事本打开 `.OCR.md`，能看到形如 `--- 第 1 页 ---` 的页标记，下面是对应文字。
❌ 如果字符极少 → 把 `--dpi` 提到 300 重跑。

### 第 4 步：标定页码（只针对扫描件）

```powershell
python -B _page_number.py "<DSH_ROOT>\example-project\01_文献\测试扫描页.OCR.md"
```

**你会看到**：一个推算出来的**偏移量**（例如 `+7`），以及"多少页与推测一致"的统计。

> **偏移量是什么**：扫描文件里"第 1 张"往往不是"纸本第 1 页"（前面有封面、版权页、序）。偏移量就是这两者的差值。
> **为什么不能手工猜**：猜错了，你论文里所有引文的页码会**整体偏移**，而且看起来都"对"。

✅ **成功的样子**：报告里能看到"该页印着该页码"的**自证**证据，且一致页数占比很高。
❌ 若差值是**散乱的**（一会儿 +7、一会儿 +13）→ 说明页眉识别有误，需人工抽查；**不要强行使用**。

### 第 5 步：转换成印刷页码（扫描件专用）

```powershell
python -B _ocr_md_to_pages.py
```

**你会看到**：生成 `.PAGES.md` 文件——**这是最终要入库的那个版本**，里面的页标记已经是印刷页码。

### 第 6 步：启动并打开工作区

```powershell
powershell -ExecutionPolicy Bypass -File <DSH_WORKSPACE>\启动DSH.ps1
```

**你会看到**：几行状态输出，最后一行是 `在浏览器里打开： http://127.0.0.1:3080`。

浏览器打开该网址 → 新建会话 → **工作目录选 `<DSH_ROOT>\example-project`**。

> ⚠️ 工作目录**必须**选对。选错了，AI 会去别的地方找数据库，然后告诉你"知识库为空"。

### 第 7 步：入库（对话）

在对话框里说：

> 把 `01_文献` 里的文件全部入库。

**你会看到**：AI 说它要调用 `kb_ingest`，然后给出结果，形如：

```
added: 3  |  skipped: 0  |  errors: 0
chunks: 812  |  vectors: 812
```

✅ **成功的样子**：`errors: 0`，且**块数与向量数相等**。
❌ 有 `errors` → 让它逐个说明原因。

> **注意**：文字版 PDF 和 Word 会直接入库；扫描件如果**没有先做第 3–5 步**，入库的会是"几乎没内容"的版本。

### 第 8 步：核查（对话）

> 检查知识库结构和元数据。

**你会看到**：文档数、块数、向量数、悬空文档数、重复文件数、页码覆盖率、元数据缺失情况。

✅ **成功的样子**：悬空文档 **0**；"哪些文档有块/向量"无异常。
❌ 悬空文档不为 0 → 说明库里有记录指向不存在的文件，需要清理或改路径。

### 第 9 步：检索验证（这一步最重要）

从你刚入库的文献里，**挑一句完整的原话**（长一点，20 字以上），在对话里说：

> 逐字检索："（贴上那句原话）"，用关键词模式。

**你会看到**：命中结果里有**文件名、章节、页码、原文片段**。

✅ **成功的样子**：那句话被**精确**找到，并且给出的页码和你翻纸本看到的一致。
❌ 找不到 → 按 3.12 的 8 步排查。

### 第 10 步：换个方法再试一次

再说：

> 用语义检索找"（换个说法，不用原话）"。

**你会看到**：即使用词不同，也能找到相关内容。

> **这一步的意义**：验证"两种检索通道都通"。只有关键词能中 → 向量那半可能有问题；只有语义能中 → 说明你的逐字匹配有问题（通常是文本里的错字或空格）。

### 第 11 步：定位到某一页（进阶）

> 在数据库里找出第 5 卷的第 294 页，把这页内容给我看。

**你会看到**：AI 用筛选条件（`filters.section`）直接取到那一页，**不到一秒**返回。

> **这个能力**是"页码主线"打通后的直接收益——也是本系统区别于"把 PDF 喂给 AI"的地方。

### 第 12 步：备份

在对话里说：

> 备份知识库。

或手工：打开 `<DSH_ROOT>\example-project\.kb\`，把 `kb.sqlite` 复制一份，改名成 `kb.sqlite.bak-20260916-练手完成`。

✅ **成功的样子**：`.kb` 目录里出现两个 `kb.sqlite*` 文件，其中一个是备份。

| 问题 | 若答案是"否"，说明 |
| --- | --- |
| 我能用一句原话精确找到它吗？ | 文本质量或检索模式有问题 |
| 找出来的页码和我翻书看到的一致吗？ | 页码偏移没标定对（**最危险**） |

| 我手上有至少一份可直接回退的备份吗？ | 你在裸奔（写库前必做备份） |

## 5.3 十个常见研究任务的操作配方

每一项都写成"**你说什么 → 系统做什么 → 怎么验收 → 坑在哪**"。可以直接照抄那些话。

### 配方 1：给论文里已有的引文补上纸本页码

**场景**：论文写完了，注释里只有"（《示例文集》第 3 卷）"，没有页码，投稿要求补全。

**你说**：
> 帮我核对 `topic-b\03_论文\xxx.md` 里的引文，找出每一条在《全集》里的页码。

**系统做什么**：拆出每条引文 → 在库里定位 → 给出候选页码 + 页内原文印证 → 两条独立路径交叉验证 → 生成候选清单文件。

**怎么验收**：每条候选都**带页内原文**；交叉验证一致率要接近 100%。
**坑**：页码是**候选**，不是结论。写进论文时保留"（待回查纸本）"，抽几条翻书确认后再删。

### 配方 2：核对"我引的这句话，原书是不是这么写的"

**场景**：审稿人质疑某条引文有误。

**你说**：
> 逐字核对这些引文和原文是否一致，列出所有差异。

**系统做什么**：把论文引文与命中页原文**逐字对比**，输出差异清单。
**怎么验收**：差异逐条列出（小到"一六年后／十六年后"这种字的差别也要出来）。
**坑**：先按省略号切段再比对——论文里用「……」跳过原文若干字，直接比对会得到一堆假的"差异"。

### 配方 3：做一个主题的综述准备（把相关文献找齐）

**你说**：
> 在数据库里找关于"示例人物乡村建设与现代化"的文献，用深度检索，列出最相关的 10 篇，标明作者、年份、刊物和页码。

**系统做什么**：深度检索（含重排序）→ 返回最相关片段 + **相关文献推荐**（同作者/同刊/年份相近/主题相似）。
**怎么验收**：结果里每篇都有出处与页码；相关文献列表可用于继续扩大阅读面。
**坑**：查询词写成术语串，别写整句问句（见 3.4.3）。

### 配方 4：查某个概念在哪几本书里出现过

**你说**：
> 逐字检索"（那个概念/短语）"，用关键词模式，把所有命中的文献和页码列出来。

**怎么验收**：命中应当**跨多篇文献**；如果只在一篇里出现，可能是这个词太特殊或文本有错字。
**坑**：OCR 错字会导致漏命中（如"示例人物"被认成"梁漱滇"）。**用关键词模式**能最大化精确匹配。

### 配方 5：把 Zotero 里的文献批量搬进数据库

**你说**：
> 把我的 Zotero 文献库搬进知识库，先试运行看要搬哪些。

**系统做什么**：读 Zotero 数据库 → 找**带 PDF 附件**的条目 → 取题录 → 逐篇入库。
**怎么验收**：试运行列出的候选数与你 Zotero 里带 PDF 的条目数一致。
**坑**：附件文件缺失的会被标记 `missing` 并跳过（**它不会替你下载**）；搬完记得再核查一遍题录质量。

### 配方 6：批量修正被程序抓错的作者/年份

**场景**：库里作者的字段值出现 `dc.cqvip.com`、`CNKI` 这种网站域名——那是程序从 PDF 元数据里**抓错**的。

**你说**：
> 检查数据库里的题录，把明显错误的作者、年份、刊物列出来，并给出修正方案（先不要改）。

**系统做什么**：扫描全部文档 → 分类列出可疑值 → 给出可核实的证据（首页提取文本里的作者署名、刊期）。
**怎么验收**：每条修正建议都**带证据**，而不是"看起来该这样"。
**坑**：
- 不要把可疑值**一律改成空**——本机实测过，看似全错的 14 条年份里，**有 3 条是真的**（首页明写当年刊期）。
- 最有效的手段是"**反哺**"：用一份已核实的题录按标题匹配回填，一次能修上百条。

### 配方 7：清掉重复文献

**你说**：
> 检查有没有内容重复的文献，保留最早入库的那份。

**系统做什么**：按内容指纹（sha256）分组，删除后来者，连同它的块和向量一起清掉。
**怎么验收**：执行后再核查一次，应显示"同指纹组 0"。
**坑**：**磁盘上的重复文件不会被删**（设计如此）。要清理磁盘文件，先确认，再自己动手。

### 配方 8：给一本书建立"按页可查"的库

**步骤**：走第 5.1 表的第 1→6 步。扫描件必须先 OCR、标定页码、转成 `.PAGES.md` 再入库。
**怎么验收**：入库后能回答"第 137 页写了什么"。
**坑**：**不要**直接把扫描 PDF 入库——那会得到一个"只有几十个字"的空壳条目。

### 配方 9：给导师/合作者交一份文献清单

**你说**：
> 把数据库里全部文献导出成清单，含作者、年份、刊物、页码，按年份排序。

**系统做什么**：从库里读题录生成表格。
**怎么验收**：清单里的年份/刊物是否可信——**先按配方 6 体检一遍**再交出去。
**坑**：不要把程序抓的题录**未经核对**直接当成果提交。

### 配方 10：把新买的书持续加进库里

**你说**：
> 把 `01_文献` 里的新文件入库。

**系统做什么**：增量扫描 → 内容没变的跳过 → 新文件切块、算向量、入库；**超过 25 个文件自动转后台**，用 `kb_status` 看进度。
**怎么验收**：`added` 数与你的新增文件数一致；`errors: 0`。
**坑**：入库前**先备份**；入库后**立刻核对计数**（文档数、块数）。

### 通用提醒

上述任何一项，只要涉及**改库**，都遵守第七篇的 8 条纪律。最要紧的还是那三条：
**先备份 → 先试运行 → 写完核对计数**。

## 6.1 检索与数据库

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| "知识库为空" | 会话工作区不是库所在目录（最常见） | 确认工作区，或显式给出 `.kb` 的绝对路径 |
| 莫名多出几十 KB 的 `kb.sqlite` | **空壳陷阱**：引擎按错误路径自动新建 | 删掉空壳；`检查环境.ps1` 会自动标出所有空壳 |
| 检索结果里的路径点不开 | 库内 `docs.path` 还是旧电脑/旧盘符的 | 用 `迁移_改路径.py` 批量改写（见 6.4） |
| 检索卡住不返回 | 引擎联网下载模型被挂住 | 设 `HF_HUB_OFFLINE=1`、`TRANSFORMERS_OFFLINE=1` 后重启 |
| 逐字引文搜不到 | 用了 hybrid/vector 模式 | 换 `mode=keyword` 再试 |
| 中文问句检索差 | 库内正文以英文/中文为主，查询词语言不匹配 | 按 3.4.3 写成术语串 |
| 结果总是同一批 | 命中了检索缓存 | 改动筛选条件，或入库一次（会清缓存） |
| 深度检索与快速检索没差别 | 重排序模型未生效（未下载） | 见 4.3；接受降级或下载模型 |
| 块数 ≠ 向量数 | 有块没算向量（本机 51 个，属历史遗留） | 用 `kb_audit3.py` 查看是哪些块；多数是参考文献（权重 0，**有意不索引**） |

## 6.2 插件与工具

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 对话里根本没有 kb 工具 | 工具在**会话创建时**注入 | 重启 DSH，**新开一个对话** |
| 有工具但一用就报"服务不可用" | `subprocess` 服务缺失 | 打 2.7 的补丁 |
| `toolkit_*` 报 `userRender is not a function` | 插件漏了 `output.render`，宿主无条件调用它（**已于 2026-09-16 修复**） | **重启 DSH 生效**；重启前用命令行 `python <REPO>/tools\toolkit.py list` |
| 升级 DSH 后知识库工具全部消失 | 新版 `subprocess` 服务在 Windows 下未生效，而 kb-rag 取不到服务就放弃注册 | 回滚，或用 `kb_cli.py` 保底（§3.13）；详见 `DSH_0.1.5_知识库修复记录_20260916.md` |
| 学术写作工具报 `value is not lossless JSON` | 该插件自身缺陷，**与本流程无关** | 不用它，或用命令行工具替代 |

| 装完插件但配置里没有 | profile 未 reconcile | 重启 DSH；或重跑 `dsh plugin --profile web add <包名>` |

## 6.3 文本与 OCR

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 双栏文献左右交错 | 旧版 OCR 按行读取 | 用新版式感知 OCR 重跑（已内置栏数判定） |
| 页眉混进正文 | 未做页眉分离 | 用 `_ocr_pdf_to_md.py`（会把页眉单独标记） |
| 页下注混进正文 | 未做脚注分离 | 同上；必要时抽查 `.quality.md` |
| 生僻字/异体字认错 | OCR 能力上限 | 无法根治；**引用时逐字核对纸本** |
| 某几页只有几个字 | 插图页或 OCR 漏识 | 看 `.quality.md` 的"过短页"清单，人工确认 |
| OCR 太慢 | 正常 | 放着跑；用 `--resume` 支持中断续跑 |
| OCR 产出的页码和纸本差几页 | 扫描件前面有封面、版权页等无页码内容 | 用 `_page_number.py` 自动标定偏移；**不要手工猜** |

## 6.4 换电脑 / 换盘符（专项）

**症状**：库能搜到内容，但结果里的文件路径指向旧电脑，点不开。

**原因**：库内 `docs.path` 记录的是**绝对路径**。

**三步解决**：

```powershell
# ① 试运行：看会改什么（不动手）
python <DSH_WORKSPACE>\迁移_改路径.py --old "<DSH_ROOT>\example-project" --new "E:\研究\example-project"

# ② 确认后执行（会自动备份数据库）
python <DSH_WORKSPACE>\迁移_改路径.py --old "<DSH_ROOT>\example-project" --new "E:\研究\example-project" --apply

# ③ 验证：库内路径在磁盘上是否都能找到
python <DSH_WORKSPACE>\迁移_改路径.py --old "<DSH_ROOT>\example-project" --new "E:\研究\example-project" --verify
```

✅ **成功的样子**：第③步显示"磁盘上找不到的文献：0 条"、"仍写着旧路径的文献：0 条"。
❌ 还有找不到的 → 说明文献文件本身没拷全，先把文件补齐。

> ⚠️ 脚本还会顺带改写**工具箱脚本里写死的路径**（本机实测涉及 84 个文件）。这是必要的——否则 OCR、页码、引文这些脚本会去旧路径找文件。

# 第七篇　数据安全与操作纪律（8 条）

1. **写库前必备份**：命名 `kb.sqlite.bak-日期-原因`，并设保留上限（本机护栏设的是保留最近 8 个）。
2. **一律先试运行**：所有写操作默认只看不改，确认无误再加 `--apply`。
3. **写后立刻核对关键计数**：文档数、块数、带页码块数——**不增反减立即回滚**。
4. **未验证的推断不写进库**：宁可留空（`NULL`），也不填一个"看起来对"的值。
5. **页码与引文一律带"（待回查纸本）"**：OCR 或推断得到的页码是**候选**，不是结论。
6. **区分原文／转述／推算**：直接引语给页码；转述只给线索；推算值必须标出来。
7. **报告与执行记录同步产出**：每轮工作留一份可复现的记录（含命令与验收数字）。
8. **不删你的素材**：可以删库内记录；**删磁盘文件必须先问过你**。

# 附录 E　新手常见问题（30 问）

## E.1 概念类

**1. 这套东西和"把 PDF 拖给 ChatGPT"有什么区别？**
拖 PDF 只能看几页，而且它记不住；这套系统把**整批文献**变成可检索的库，并且记住"这句话在纸上第几页"。区别的核心是**可引用**——你能把结果写进论文注释并回查纸本。

**2. 我需要会编程吗？**
基本使用**不需要**。入库、检索、问答都在对话里说人话就行。只有处理**扫描件**（要 OCR、要标定页码）时需要照文档抄几条命令。

**3. 我的文献会被上传到网上吗？**
分两件事，必须说清：
- **入库、检索、认字、算向量，全部在你本机完成**（数据库是一个本地文件，检索模型也是本地运行）——这部分的**内容不会上传**；
- 但是，**检索出来的片段会进入对话**，而对话要发给模型服务才能生成回答。准确说法是："**不会全量上传，但被检索命中的片段会随对话发送**"。
如果你有不能外发的材料，把它排除在入库范围外，或改用不联网的方式自己检索（用 `mode=keyword` 直接看结果，不要求 AI 作答）。

**4. 一次能放多少书？**
实测百余篇 / 万块级 / 数十 MB，跑得很轻松。上限主要看硬盘和耐心（扫描件慢）。**建议分批入库**，每次几十篇，便于发现问题。

**5. 中文书和英文书能放在一个库里吗？**
能，但**检索时要注意查询词的语言**：库内以中文为主就写中文术语串，以英文为主就写英文术语串。引擎不会替你翻译。

**6. 扫描件和普通 PDF 有什么区别？**
普通 PDF 里**本来就带文字**，可以直接入库；扫描件是"照片"，必须先**认字（OCR）**。用 `_pdf_scan_check.py` 一测就知道。

**7. 为什么系统老强调"页码"？**
因为你写论文要引注。没有页码，AI 找到的内容你**没法引用**——审稿人一问就露馅。

## E.2 使用类

**8. 我可以说中文吗？**
可以，你说的每句话 AI 都懂。但**检索库内文献时，查询词要用对应的语言**（见第 5 问）。

**9. 为什么有时候搜不到明明有的内容？**
按 3.12 的 8 步排查。最常见的三个原因：**工作区选错**（在查另一个空库）、**查询词语言不对**、**用 hybrid 模式做逐字核对**（应换 `keyword`）。

**10. 结果里的页码可以直接写进论文吗？**
**这是本指南最重要的一问**：不可以直接写。OCR 和推断得到的页码是**候选**，正确做法是——
① 系统给的页码只当"候选"；② 抽几条**翻纸本确认**；③ 未经确认的一律标注"（待回查纸本）"。
页码的可靠性是这套系统的生命线。一旦整体偏移，你所有引注都会错，而且**看起来都对**。

**11. 会不会编造文献或页码？**
系统在规则上**禁止编造**：库里没有的就说没有，页码推不出来就**留空**。但任何自动系统都可能出错，所以纪律是"留空胜过猜测 ＋ 关键处人工抽查"。

**12. 入库要多久？**
实测约 **8.9 块/秒**（2,121 块用 239.6 秒）。1000 页的书约 5–15 分钟。扫描件另算——OCR 约 **5 页/分钟**，700 页要 2–3 小时，建议过夜跑。

**13. 为什么第一次检索很慢？**
引擎要加载嵌入模型（实测约 5.7 秒）并预热。第一次可能几十秒，之后就快了。相同查询与筛选条件会走**缓存**直接返回。

**14. 加新文献会不会把旧的搞乱？**
不会。入库是**增量**的：内容没变的文件按指纹跳过，只处理新文件和改动过的文件。

**15. 同一个文件放在两个文件夹里，会重复入库吗？**
不会。系统按内容指纹识别重复并跳过。

**16. 我改了某个文件的内容，要做什么？**
重新入库那一个文件即可（它会自动识别内容变了）。

**17. 想删掉某篇文献怎么办？**
在库内删记录即可（有专门工具），**磁盘上的原文件不会被删**——这是刻意设计，避免误删你的素材。

## E.3 数据安全类

**18. 数据会不会丢？**
"写库前备份"是硬纪律。备份就是一次文件拷贝，命名 `kb.sqlite.bak-日期-原因`。护栏脚本会自动做，你自己也应当定期做。

**19. 备份要多久做一次？**
每次**批量改动之前**必做；平时每周一次。注意设**保留上限**（本机设的是保留最近 8 个），否则磁盘会被备份吃掉。

**20. 备份文件放哪比较安全？**
**不要只放在同一个文件夹**。至少另拷一份到移动硬盘或另一个盘——本机曾一次性清理掉全部历史备份，之后就没有本地回退点了。

**21. 换电脑会怎样？**
库可以整个拷过去，但**必须做一次路径迁移**（见 6.4），否则结果里的文件路径点不开。这一步最容易漏。

**22. 数据库能改名吗？**
`.kb` 目录名和 `kb.sqlite` 文件名**不能改**（工具写死了）。要让名字好看，改**它们外面那层文件夹**的名字。

**23. 我在别处乱敲命令，会不会把库弄坏？**
最可能造成伤害的是"在错误的目录下使用默认路径"——引擎会在那里**悄悄新建一个空库**。识别方法：真库几十 MB，空壳只有几十 KB。`检查环境.ps1` 会自动标出所有空壳。

## E.4 学术规范类

**24. 用这套系统查资料，算不算学术不端？**
工具本身中性，**风险在用法**：把 AI 生成的内容当原始文献引用、或未经核对就写页码，这才是问题。正确用法是：**用它定位、用你核对过的原文引注**。

**25. 引注格式能自动生成吗？**
可以（支持 GB/T 7714 等常用格式）。但**元数据（作者/年份/刊物）必须核实**——程序从 PDF 里抓的题录错误率不低，本机实测曾抓到"作者是网站域名"这种值。

**26. 参考文献要不要入库？**
系统的行为是：参考文献**存下来但权重设为 0**，即**不参与正文检索**。所以检索正文时不会被参考文献刷屏，需要时又能查到它们。

**27. 我应该整本书入库，还是只入相关章节？**
建议**整本入库**（页码连续，缺卷会导致引文找不到），检索时再用筛选条件收窄范围。

**28. 库里的内容能导出给别人吗？**
技术上可以（数据库就是一个文件）。但注意**版权**：扫描件与全文的分享受法律限制，请按合规方式处理。

**29. 多久重新核查一次库？**
建议：**每次批量入库后**核查一次（结构 ＋ 计数）；**每学期**做一次全面体检（元数据缺失、重复文件、页码覆盖率）。

**30. 这套流程最容易被忽略、却最要命的是什么？**
**页码口径的统一**。三种来源（扫描页序、Word 页眉、扫描页页眉）如果不统一成"印刷页码"，你的引注会**看起来都合理、实际互相矛盾**。这一条比任何技术细节都重要。

---

> **最后一句**：数据库的可靠性**不取决于向量模型有多强**，而取决于"页码这条线"有没有从扫描页一路贯通到论文注释。
> 这一路上最危险的不是"读不出来"，而是"**读错但看起来对**"——所以每一步都要留下依据，**留空胜过猜测**，写完立刻校验。
