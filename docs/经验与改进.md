# 一、新增经验总结

## 1.1 一句话

> **建库的难点在"读得准"，运维的难点在"改得稳"。** 09-15 之前的教训几乎都关于前者（OCR、页码、双栏）；09-16 这一轮全部关于后者——**一次版本升级、一次目录改名，就能让整套检索能力静默失效，而数据一个字节都没坏。**

这句话是本次最大的认知变化：**环境本身也是需要被管理的数据**。

## 1.2 这一轮发生的四件事

| 事件 | 结果 | 代价 |
| --- | --- | --- |
| DSH `0.1.1-rc.2 → 0.1.5-rc.1` 升级 | ✅ 最终成功，未回滚 | 约 4 小时排障；期间知识库工具**完全不可用** |
| 数据库迁移（嵌套目录 → 工作区根）+ 工作区改名 | ✅ 完成，114 条路径全部可解析 | 改写 **84 个活件 + 4 处拼接式引用** |
| 桌面快捷方式 + 启动器 | ✅ 通过 9 项可靠性验证 | 发现并修掉 2 个缺口 |
| 全面核查数据库 | ✅ 健康；两项遗留疑问结案 | —— |

## 1.4 新增的坑（09-15 之后才踩到的）

1. **环境升级会让插件静默失效，且不报错。**
   DSH 0.1.5 把 `subprocess` 提供方换成 `@deepseek-ai/dsh-subprocess-local`；`kb-rag` 因**并发加载竞态**抢跑取不到服务，于是**直接放弃注册全部 10 个工具**——日志只有一行，界面一切正常，检索会说"知识库为空"。

2. **"服务不存在"与"服务注册得晚"是完全不同的两件事。**
   我最初判成前者，据此建议回滚。真相是后者（竞态）。**反证其实早就在日志里**：同一 boot 中另一个插件能拿到 base 层的 `tools`/`timer`，说明跨层可见性正常。教训：**"取不到"要先问"是没注册，还是我取早了"。**

3. **npm 11 默认拦截安装脚本**（allow-scripts）。
   新装的 `koffi` 因此没有原生模块；而它是 6 个核心包的依赖。**升级后不能只看版本号**，要验证依赖真的可用。

4. **`file:` 安装的本地插件是"副本"，不是符号链接。**
   改了源码目录，运行中的服务仍加载 `node_modules` 里的副本——本次一度据此误判。（后核实两者哈希一致，真因是另一处。）

5. **目录改名会打断三样东西**：库内 `docs.path`（114 条）、脚本里的硬编码路径（84 个文件）、DSH 的工作区注册表。少改任何一样都会"能搜到但点不开"或"工作区消失"。

6. **空壳库陷阱会复发。**
   01:19 在旧路径下又被自动生成了一个 32 KB 空库，并让注册表多出一条**指向空库的工作区**——点进去查的是空库，极易误判成"数据丢了"。

7. **运行中的服务会锁文件**（`libvips-42.dll`），导致重装必然 EBUSY；**任何重装/回滚都必须先停服务**。

8. **新版 DSH 的界面要 token，且每次启动都变**——网址不能写死，必须"启动后从日志取并验证"。

9. **含中文的 `.ps1` 必须是 UTF-8 带 BOM。** 本次因此返工 3 次（PS 5.1 会按 GBK 解析并直接报语法错误）。

10. **PowerShell 里内联 python 传中文会互相打架**（`\"` 转义、GBK 控制台、`: ` 被当驱动器变量）。凡是带中文的逻辑，一律写成脚本文件再执行——本次因此浪费了若干次往返。

## 1.5 本次真正靠得住的四个方法（建议作为标准手段）

| 方法 | 怎么用 | 本次实例 |
| --- | --- | --- |
| **对照实验** | 把怀疑对象**移除**再跑，看现象是否变化 | 删掉我方补丁的两行 → 报错一字不差 ⇒ 排除补丁 |
| **隔离复现** | 用假 ctx + 垫片 node_modules 把插件单独跑起来，抓真实堆栈 | 一次拿到 `validateNoNullByte ← targetEnvironment ← spawn` 的完整调用链 |
| **读上游注释** | 插件作者常把"为什么这么写"写在代码里 | kb-rag 1.6.7 的注释直接点明并发竞态 |
| **分别验证两条路径** | 同一工具往往有"平台路径"和"回退路径"，只测一条会漏 | toolkit 的回退路径正常、平台路径因缺 `cwd` 崩溃——这正是长期没被发现的原因 |

## 1.6 我自己的两次误判（如实记录）

| 误判 | 真相 | 教训 |
| --- | --- | --- |
| "subprocess 提供方在 0.1.5 下未生效，建议回滚" | 服务正常，只是比消费方注册得晚（竞态） | 无报错 + 取不到 ≠ 没加载；**并发时序**必须列为竞争假设 |
| "toolkit 工具坏 = 与 kb-rag 同类的竞态，补 inject 即可" | 真因是 `spawn` 规格缺 `cwd`，平台服务对 `spec.cwd` 做空字节校验 | 同类现象不等于同一原因；**要用堆栈定位，不要用类比定位** |

两份原始报告都已加**更正声明**并标明以更正为准——错判留在记录里会误导后续排障。

# 二、工具使用建议

## 2.1 参数化：现在的可复用性很差（有实测数据）

对 `_toolkit` 下 83 个脚本做过分级（判据：是否 argparse／有无绝对路径字面量／有无项目专名）：

| 级别 | 判据 | 数量 | 复用方式 |
| --- | --- | --- | --- |
| **A 通用** | argparse 且无硬编码 | **3** | 直接可用于新项目 |
| **B 半通用** | argparse 但默认值写死 | 31 | 加参数覆盖 |
| **C 项目专用** | 非 argparse 且含专名/路径 | **49** | 只能当模板参考 |

**建议（按性价比排序）**：

| # | 建议 | 做法 | 成本 |
| --- | --- | --- | --- |
| 1 | **消灭 `DB = r"D:\..."` 这类库路径常量** | 统一改为 `--kb-root`/`--db`，缺省从环境变量或 `.kb` 推断；改一个共用 `config.py` 即可辐射 30+ 脚本 | 1–2 小时 |
| 2 | **给审计类脚本加 `--json`** | 目前多数只打印给人看，无法被程序消费；加了之后可自动巡检 | 每个 10 分钟 |
| 3 | **把"一次性侦察脚本"与"常备工具"分开** | 现在两者混在一起（见 2.2） | 半小时 |
| 4 | 给 `_docx_pages_to_md.py` 去掉写死的卷号 `[2,3,6,7,8]` | 改为必填参数 | 10 分钟 |

## 2.2 索引卫生：诊断脚本污染了工具库

本次我建了约 20 个一次性诊断脚本（`_probe_*.py`、`_healthcheck_*.py`…），它们**全部被自动登记**进工具库索引——索引从 87 涨到 126 条，其中相当一部分是"只为查一个问题而存在"的。

**建议**：

- 约定前缀：`_probe_*`/`_once_*` 表示一次性，**不登记**（在插件里加一条忽略规则）；`_tool-*`/无前缀表示常备工具。
- 或者放到独立目录（如 `<REPO>/tools\_scratch\`）并加入 `ignore_dirs`。
- 定期用 `toolkit.py audit` 复盘：本次审计显示 **50 个脚本含硬编码绝对路径、57 个无参数**（只能开编辑器改路径才能用）——这两个数字应当作为技术债指标持续跟踪。

## 2.3 写库护栏制度化（现状已经很好，建议再进一步）

- 现状：`_kb_guard.py` 提供备份→断言→单事务→写后校验，自测 7 项全过。
- **建议**：把"任何直接改 `kb.sqlite` 的脚本必须经 `KbGuard` 进出"写成硬约束，并在 `toolkit.py audit` 里加一条检查：**扫描哪些脚本直接 `sqlite3.connect(kb.sqlite)` 却没有 import 护栏**。

## 2.4 工具自身的验证

- 现状：只有 `_kb_guard.py` 有 `--selftest`。
- **建议**：给三类高危工具补自测（各 10–20 行）：
  ① 写库类  ② 移动/改名文件类  ③ 生成可被人引用的产物类（如 `md2docx`、`_insert_page_numbers`）。
- 本次 `md2docx-unified` 暴露过一个真实缺口：**完全不处理 ``` 代码块**（块内 `# 注释` 会被当成标题、围栏本身会变成正文）。我已给它补上代码块与"引用块内代码块"的支持并做了回归，但**这类缺口本该由自测先发现**。

## 2.5 环境类工具应常备

现有 `检查环境.ps1`（就绪检查）很好用，建议扩充为**变更后验收**脚本：一次跑完
① DSH 版本与端口 ② 插件实装与加载 ③ **kb 工具是否真的注册**（不能只看日志）④ 工作区注册表 ⑤ 数据库完整性与计数 ⑥ 检索冒烟（一次 keyword + 一次 hybrid）。

# 三、工作流程建议

## 3.1 升级 DSH：定为"变更事件"，而不是随手装

你 09-16 写的那份《升级操作预案》方向完全正确，建议把它固化为常备流程，并补三条来自本次实测的检查点：

| 阶段 | 动作 | 关键检查点（本次实测得来） |
| --- | --- | --- |
| 前置 | **先把上游插件升到已修版本**（本次是 kb-rag ≥1.6.7） | 只升 DSH 不升插件 = 知识库必挂 |
| 前置 | 备份 profile（`package.json`/`pnpm-lock.yaml`/`cordis.patch.yml`）+ 记录当前版本 | 回滚要靠它 |
| 前置 | 在**隔离 home** 里演练（`D:\dsh-lab-home`） | 你已做到 |
| 执行 | **先停服务**再装（否则 EBUSY） | 服务会锁 `libvips-42.dll` |
| 执行 | 装完**验证依赖真的可用**（如 koffi 的原生模块） | npm 11 会拦安装脚本 |
| 执行 | **用带日志的方式启动** | 无日志 = 排障失明 |
| 验收 | ① 版本 ② 端口 ③ **插件工具真的注册**（实调一次） ④ 工作区注册表 ⑤ 检索冒烟 | 只看版本号会漏掉"工具没注册" |
| 回退 | 回滚**必须连 profile 一起还原** | 否则卡在"程序退回、配置没退回"的夹缝 |

**另建议一条硬规则**：升级后用**一个新会话**验证（工具在会话创建时注入），不要只信老会话的表现。

## 3.2 数据库变更（迁移/改名/重灌）

本次迁移漏一处就会出事，建议固化为清单：

1. **先体检**：`PRAGMA integrity_check` + 记录 docs/chunks/vecs 基线计数；
2. **改名/移动**：库固定为 `<工作区>\.kb\kb.sqlite`——**`.kb` 与 `kb.sqlite` 这两个名字永远不要改**，要改就改它们外面那层文件夹；
3. **改写库内路径**：`docs.path` 前缀（本次 114 条）+ 清空 `cache`；
4. **改写活件里的硬编码**：脚本与配置（本次 84 个文件 + 4 处拼接式引用——**拼接式的最容易漏**，如 `SUB / ".kb" / "kb.sqlite"`）；
5. **同步 DSH 工作区注册表**（`storages\workspace.json`）；
6. **验证**：库内路径全部能在磁盘解析 + 计数不变 + 完整性 ok + **实际检索一次**；
7. **清理**：删掉旧位置副本与空壳库；**并确认旧路径下不会再有东西自动生成空库**。

**建议加一条预防措施**：在 `检查环境.ps1` 里检测"是否存在 <50 KB 的 `kb.sqlite`"，发现即报——空壳陷阱已经复发过一次。

## 3.3 备份策略（本次最大的缺口）

- 事实：09-15 按你的决定删掉了 7 个库备份；此后**长达一天多没有新备份**，直到本次核查才发现。
- **建议**：
  ① **写库前后各一次**（护栏已自动做）；
  ② **每周一次冷备份到工作区之外**（本次已建 `D:\kb-backups\`）；
  ③ 设**保留上限**（如最近 8 个）以免吃盘；
  ④ 关键节点（迁移、升级、重灌前）**额外留一份**；
  ⑤ 把"备份是否存在、最近一次何时"纳入定期核查——本次就是靠核查才发现的。

## 3.4 环境变更后的验收清单（建议常备）

任何"动过环境"的操作（升级插件、改 profile、改注册表、改启动方式）之后，跑这五项：

1. `kb_stats` 能返回真实计数（**不是** unknown tool、**不是** 0 文档）；
2. 一次 `kb_search`（默认模式）返回真实命中且带出处；
3. `toolkit_list` 能返回工具列表；
4. 工作区注册表里 7 个条目路径全部存在；
5. `启动DSH.ps1` 的日志里没有 `tools not registered` / `auto-register error`。

## 3.5 文档与记录纪律（本次做得好，建议保持）

- **报告要留"更正声明"**：本次两份报告都因判断有误而补了更正段落，并标明以更正为准。
- **区分"事实/推断/建议"**：本文即按此标注。
- **记录要含可复现命令**：否则事后无法复核（本次所有结论都附了命令）。
- **验收要写清"没测什么"**：捷径方式的可靠性报告明确列出三项未验证场景——**不写，就等于默认全测过**。

> **一句话收尾**：
> 数据本身这次一个字节都没坏，坏掉的是**"我以为它在正常工作"**。
> 所以运维的可靠性与建库不同——它不靠更仔细，**靠的是每次变更后都用一条命令去问系统"你现在真的还能用吗"**。
