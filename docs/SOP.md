# 文献库构建 SOP（可复用版 v1.0）

> **这份文档是什么**：把「扫描件／PDF／Word → 可检索、可按印刷页引用的文献库」的全过程，统一成一套**与具体项目无关**的流程、验收门、工具清单与失败模式。
> **这份文档不是什么**：不是某本书的项目记录。项目实测数字一律放在**附录 A**，正文只写规范。
> **适用**：任何需要"文献全文可检索 + 引文能落到印刷页码"的研究项目（书籍、期刊论文、档案扫描件、docx 文稿）。
> **首次成文**：2026-09。**依据**：一个真实研究项目的实际作业过程（该项目数据不随本仓库公开）（详见附录 A），全部工具调用方式均经 `--help`／源码核对，非转抄。

---

## 0. 两条不变式（整条流水线的判据）

**不变式 1：页码是主线。**
从扫描页开始，页码就要落进文本标记，一路贯通到入库后的 `section` / `page_start`，再到论文里的引文标注。**这条线一断，后面全是猜**——检索能返回文本，但你无法回答"这句话在原书第几页"。

**不变式 2：宁可留空，不可猜测。**
流水线上最危险的不是"读不出来"，而是"**读错但看起来对**"。所以：读不出来 → 如实记 `status`；推不出页码 → 留 `NULL`；没核实 → 标"待回查纸本"。

> 这两个不变式能解释下面几乎所有的设计选择。若项目不需要"引文可回查纸本"，可以砍掉阶段 2、5，但**不要**用"承前/承后"之类的兜底去伪造页码。

## 1. 五层架构

```
L1 素材层    原始 PDF / DOCX / 扫描件 / 已有 Markdown
                 ↓  体检：页数、有无文字层、版式类型
L2 文本化层  三条并行路线，按素材类型择一（可混用）
                 ① 版式感知 OCR        ← 无文字层的扫描件
                 ② docx 页眉法（免OCR） ← "一页一节"且页眉带页码的 docx
                 ③ OCR 文本转印刷页码   ← 已有 OCR，但页码是 PDF 页序
                 ↓  产出：逐页文本 + 页标记 + 质量报告
L3 结构层    分块 + 页码字段 + 向量（kb_ingest）
                 ↓
L4 应用层    检索 / 引文定位 / 逐字校勘 / 页码回填 / 二级文献抽取
                 ↓
L5 治理层    结构核查 / 去重 / 元数据修复 / 备份与回滚
```

**设计要点**：页码在 **L2 就要落进文本**（作为 `#### 第 N 页` 之类的页标记），不要留到 L3 之后再补。L3 的切块器会把页标记抽成 `chunks.section`，检索结果直接可见、可用 `filters` 精确取某页——这是"引文可回查"的实现方式。

## 2. 十二步流程

每一步都给：**输入 → 做法 → 工具 → 产物 → 验收门（DoD）→ 不达标的处置**。

### 步骤 1　素材体检

| 项 | 内容 |
| --- | --- |
| 输入 | 待入库的全部素材（PDF/DOCX） |
| 做法 | 逐件取页数、判断**有无文字层**、文字层质量、能否识别印刷页码 |
| 工具 | `_pdf_scan_check.py` |
| 产物 | 素材清单（含 `status`：正常 / `no_text_layer` / 无页码线索） |
| **验收门** | 每件素材的页数已知；`no_text_layer` 的**单独列出** |
| 不达标 | 无文字层 → 进步骤 3 的 ① 路线；页数异常 → 先查文件是否损坏 |

> ⚠️ **"未入库"≠"被遗漏"**。曾把两篇"缺失文献"当成缺口，实为纯图像（提取出 19 字、39 字）。**先看 `status`，再谈缺口。**

### 步骤 2　版式预检

| 项 | 内容 |
| --- | --- |
| 做法 | 抽样多页（首页＋均布＋末页）判定：栏数、通栏、页眉页脚、页下注、竖排、注释体系、引用格式 |
| 工具 | `_ocr_layout.py` |
| 产物 | `.layout.json`（逐页版式参数）＋ 警告清单 |
| **验收门** | 栏数判定有依据；低置信页列入清单 |
| 不达标 | 版式差异大的，**逐页使用各自的栏参数**，差异写入警告 |

### 步骤 3　文本化（三条路线择一）

| 路线 | 适用 | 工具 | 产物 |
| --- | --- | --- | --- |
| ① 版式感知 OCR | 扫描件、无文字层 | `_ocr_pdf_to_md.py` | `.OCR.md` ＋ `.OCR.layout.json` ＋ `.OCR.quality.md/.json` |
| ② docx 页眉法 | 一页一节的 docx，页眉含页码 | `_docx_pages_index.py` → `_docx_pages_to_md.py` | `.PAGES.md` |
| ③ OCR 文本转印刷页码 | 已有 `.OCR.md`，页码还是 PDF 页序 | `_ocr_md_to_pages.py` | `.PAGES.md` |
| 附：docx 全文抽取 | 已有 docx 成品，要正文＋脚注＋尾注 | `_docx_full_text.py` | `.full.md` |

**验收门**：逐页文本齐备；页标记连续；页眉／页下注与正文**分离**；低置信页有清单。
**不达标**：低置信页人工复核或重跑（提高 dpi／换 profile）。

### 步骤 4　页码标定

| 项 | 内容 |
| --- | --- |
| 做法 | 从页眉数字**投票**求偏移量，再用"相邻页 +1 连续"做结构校验；分段检测偏移突变 |
| 工具 | `_page_number.py`、`_verify_page_offset.py` |
| **验收门** | 偏移量**自证**：命中页文本里真的印着推算出的页码；一致页数占比高且差值**成片**（散点＝OCR 误识，成片＝偏移变了） |
| 不达标 | 偏移算不出 → 手工试并记录依据；始终算不出 → 该卷页码标"不可用" |

### 步骤 5　统一页码口径

| 项 | 内容 |
| --- | --- |
| 做什么 | 把三种来源（OCR 的 PDF 页序 / docx 页眉 / 扫描页页眉）**全部换算成印刷页码**，偏移归零 |
| 工具 | `_ocr_md_to_pages.py`（可 `--offset` 覆盖） |
| **验收门** | 全库页标记＝**印刷页码**；`section` / `page_start` 一律存印刷页；换算前后引文页码**逐条一致** |
| 不达标 | 不一致的逐条列出，人工裁定 |

> 页码有三种来源，**口径不统一是最隐蔽的坑**：同一批引文在不同卷里会按不同基准标注页码，看起来都"对"。

### 步骤 6　入库

| 项 | 内容 |
| --- | --- |
| 工具 | DSH 工具 `kb_ingest`（**必须显式传 `kb_root`**） |
| 产物 | 库内 docs / chunks / vecs 记录 |
| **验收门** | 新增/更新/跳过/错误**条数明确**；块数与向量数相等；内容未变的文件被跳过（增量） |
| 不达标 | 批量任务转后台 → 用 `kb_status` 轮询；错误逐条看原因 |

### 步骤 7　结构核查

| 项 | 内容 |
| --- | --- |
| 工具 | `_kb_audit2.py`（结构/分块/页码/重复/向量）、`_kb_audit3.py`（细部）、`_kb_coverage_vs_files.py`（磁盘 vs 库）、`_kb_meta_gaps.py`、`_kb_dup_inspect.py` |
| **验收门** | 悬空文档 0；`chunk_count` 与实际块数**零不一致**；无同 sha256 重复；页码字段覆盖率**记录在案**；元数据缺失面**量化** |
| 不达标 | 见步骤 12 治理 |

### 步骤 8　检索能力验证

| 项 | 内容 |
| --- | --- |
| 工具 | `kb_search`（三种 mode）＋ `_kb_find_text.py`（这句话落在哪个块） |
| **验收门** | 取几条**逐字引文**，`mode=keyword` 能 Top-1 命中；`filters.section` 能定位到"某卷某页" |
| 不达标 | 逐字命中不了 → 查文本化阶段的空格／双栏／异体字问题 |

> ⚠️ **逐字核实必须用 `keyword`**。实测一条 23 字原句：keyword Top-1 精确命中，而 hybrid / vector 都进不了前 3——融合排序把精确匹配摊薄了。**概念检索则相反**，hybrid 明显更好。

### 步骤 9　引文定位

| 项 | 内容 |
| --- | --- |
| 做法 | 论文引文 → 印刷页码候选：给出页码、相似度、页号自证、页内原文 |
| 工具 | `_cite_page_candidates.py`、`_resolve_full_pages.py`（无扫描件的卷用 docx 逐页索引） |
| **验收门** | 每条候选都有**页内原文**印证；相似度低的单独标出 |

### 步骤 10　交叉验证

| 项 | 内容 |
| --- | --- |
| 做法 | **两条独立路径**算同一批引文的页码，比对是否一致 |
| 工具 | `_crosscheck_pages.py`、`_spot_check_pages.py` |
| **验收门** | 一致率达标（不一致的逐条裁定）才允许写入论文 |
| 理由 | 单条路径"自证"会共同犯错；两条独立路径一致才是真证据 |

### 步骤 11　回填与校勘

| 项 | 内容 |
| --- | --- |
| 做法 | 把确认的页码写回论文标注；把论文引文与命中页原文**逐字对比** |
| 工具 | `_insert_page_numbers.py`（默认试运行，`--apply` 才落盘、自动备份）、`_quote_collation.py`、`_verify_cite_context.py` |
| 产物 | 引文校勘清单（每处差异） |
| **验收门** | 差异逐条列出；不确定的一律标"**待回查纸本**" |

> **页码定位成功 ≠ 引文无误**。实测发现过"一六年后／十六年后""哀象／衰象"这类差异，也发现过**文本归属错误**。校勘是独立的一步，不能省。

### 步骤 12　治理

| 项 | 内容 |
| --- | --- |
| 做什么 | 去重、删悬空、补元数据、更新索引、清理废弃产物 |
| 工具 | `_kb_delete_doc.py`（默认试运行）、`_kb_dedup_keep_vectors.py`、`_kb_clean_empty_pdfs.py`、`_p0_fix_kb.py`（批量元数据修复，可试运行） |
| **前置** | **写库必经 `_kb_guard.py`**（备份→断言→单事务→写后校验） |
| **验收门** | 备份存在；写后关键计数**不增反减即报警**；修复逐条留证 |

## 3. 产物与命名规范

统一后缀，让下游脚本与人都能按名识别产物（本规范取自实际约定，见附录 A 的实测计数）：

| 后缀 | 含义 | 生成者 |
| --- | --- | --- |
| `*.OCR.md` | OCR 逐页文本（含页标记、页眉/页下注标记） | `_ocr_pdf_to_md.py` |
| `*.OCR.layout.json` | 逐页版式参数（栏数、页眉、脚注带） | `_ocr_layout.py` |
| `*.OCR.quality.md` / `.json` | 质量报告：逐页问题清单＋低置信框坐标 | `_ocr_pdf_to_md.py` |
| `*.OCR.docx` | 带页标记与分页符的 Word（每 PDF 页一页） | `_ocr_md_to_docx.py --page-breaks` |
| `*.PAGES.md` | **入库用**：页标记＝**印刷页码**（`#### 第 N 页`） | `_docx_pages_to_md.py` / `_ocr_md_to_pages.py` |
| `*.full.md` | 正文＋脚注＋尾注全文（docx 抽取） | `_docx_full_text.py` |
| `manifest.json` | 素材清单与 `status`（含失败类型） | 体检阶段 |
| `kb.sqlite.bak-<时间戳>-<原因>` | 写库前备份 | `_kb_guard.py` |

**入库用 `.PAGES.md`，不要直接入库 `.OCR.md`**——除非该卷页码尚未换成印刷页码而你能接受这一点。

## 4. 知识库数据模型（参考）

引擎自动建表，四张表（**本项目实测的 schema，字段填充率可作基准线**）：

```sql
docs(id, path UNIQUE, title, authors, year, journal, doi, kind,
     sha256, size, mtime, chunk_count, indexed_at, zotero_key, indexed_with)

chunks(id, doc_id → docs(id) ON DELETE CASCADE, section, weight DEFAULT 1.0,
       seq, text, para_start, para_end, page_start, page_end)

vecs(chunk_id PRIMARY KEY, vec BLOB)      -- 向量
cache(key PRIMARY KEY, payload, created)  -- 检索缓存
索引：idx_chunks_doc(doc_id)
```

**关键约定（踩过坑才知道的）**：

1. **切块器把 Markdown 标题抽成 `chunks.section`，并从正文里去掉**。所以"这页有没有页码"**不能靠扫正文**，要看 `section` / `page_start`。
2. `chunks.weight = 0` 与"无向量"完全重合，且**全是 `References`**——那是引擎**有意不索引参考文献**，不是缺陷。误读成"向量缺口"会白忙。
3. `filters.section` 可以精确取"某卷某页"，因为页标记成了 `section`。
4. 元数据是**抽取器猜的**，必须体检（见步骤 7、失败模式 §6-D）。

| 工具 | 用途 | 关键参数 |
| --- | --- | --- |
| `kb_ingest` | 入库/增量 | `paths`、`rebuild`、`metadata_only`、`force` |
| `kb_search` | 混合检索 | `query`（**英文术语串**）、`mode`(keyword/vector/hybrid)、`depth`、`filters` |
| `kb_stats` | 规模与最近入库 | `kb_root` |
| `kb_rag` | 基于证据作答 | `query`、`depth`、`strict` |

> ⚠️ **两个必知的环境陷阱**（实测）：
> 1. **`kb_root` 默认是"当前会话工作区下的 `.kb`"**。跨项目查库必须**显式传绝对路径**，否则返回"知识库为空"而你会以为数据丢了。
> 2. **`toolkit_*` 那一组工具（list/search/show/run/scan/audit/doctor/register）此前全部报 `output.render failed: userRender is not a function`**——插件未给 `output` 提供 `render`，而宿主无条件调用它（新版 DSH 写法相同，所以换版本修不好）。**已于 2026-09-16 补齐，重启后生效**；重启前改用命令行 `python <REPO>/tools\toolkit.py <命令>` 或各工作区的 `.tools\run.py`。

## 6. 失败模式与对策（按阶段）

### A. 文本化阶段

1. **引号配对整体错位**——直引号开闭同形，窗口内奇数个就错开一位，抓到的其实是引文**前面**的正文。
   → 全文一次配对（`_quote_spans.py`），不要在小窗口里配对。
2. **省略号不能当噪声删**——论文用「……」跳过若干字，删号后前后两截被强行接成一句，永远对不上。
   → 先按省略号切段，逐段定位，再核对各段是否同页。
3. **双栏按行读会左右交错**，逐字引文永远搜不到。
   → OCR 前预检栏数，按"先左后右"读。**框坐标是渲染像素，判栏要用像素宽度而非 PDF 点宽度。**
4. **一篇文献的版式可能逐页不同**（首页单栏、正文双栏）。
   → 预检抽样多页，逐页用各自参数，差异写警告。
5. **页眉不能按"在顶部"判定**——双栏时两栏首行都在顶部，会整片误判。
   → 页眉判据＝**短行 ＋ 与正文有明显空白 ＋ 跨页复现**（刊名/书名固定，正文首行不重复）。
6. **页眉里往往印着印刷页码**——书籍页码最可靠的来源。
   → 页眉单独成行，供换算与自证。
7. **页下注必须与正文分离**（小字＋被横线/大空白隔开）。
   → 几何判定（下半部最大行间空白＋字号显著更小），引用时区分。

### B. 页码阶段

8. **页码三种来源，口径必须统一**（PDF 页序 / docx 页眉 / 扫描页页眉）。
   → 一律换算成印刷页码、偏移归零。
9. **偏移量必须自证**：命中页文本里要真的印着推算出的页码；再全卷逐页比对，看差值是否**成片**。
10. **"承前/承后"兜底会编造页码**。卷首（说明、题记）本无印刷页码，兜底会把它填成"最后一页"。
    → **卷首单独识别、留空**；匹配不到就留空。
11. **写库必须加防呆断言**：参数顺序写反会让 `WHERE id = 页码` 静默写错列。
    → 写前断言取值范围，写后核对关键计数（**不增反减即异常**）。
12. **两条独立路径交叉验证**比单条自证强。

### C. 检索阶段

13. **逐字核实用 `keyword`；概念检索用 `hybrid`**（见步骤 8）。
14. **`weight=0` ≠ 向量缺口**（见 §4 约定 2）。
15. **`filters.section` 是"定位某页"的正路**。

### D. 元数据阶段

16. **抽取器很会"抓错但看起来合理"**：作者抓成网站域名、年份抓成 **PDF 创建年**、DOI 从正文抓别人的、标题抓成刊名。
    → 入库后必做元数据体检；**凡"看起来整齐"的字段都要抽样核对**。
17. **最有效的修复是"反哺"**：用一份已核实的题录（作者/刊物/年份）按标题匹配回填主库，一次可补上百条，比逐条人工快两个数量级。
18. **不要一律把可疑值改成 NULL**：看似错的值里可能有一部分**是真的**（如首页明写当年刊期）。先查证据再改。

### E. 工程纪律

19. **每一步都要能回答"依据是什么"**：文件路径＋行号 / 命令 / 页内原文。
20. **废弃产物要及时归档**：失效的索引仍占空间，README 还在指引用它——比没有更糟。

## 7. 操作铁律（8 条）

1. **写库前必备份**：`kb.sqlite.bak-<时间戳>-<原因>`，并设保留上限。
2. **一律先试运行**：所有写操作默认 dry-run，`--apply` 才落盘。
3. **写后立刻校验关键计数**：文档数、块数、带页块数、元数据缺失数；**不增反减立即回滚**。
4. **未验证的推断不写进库**：宁可 `NULL`，也不填"看起来对"的值。
5. **页码与引文一律带"（待回查纸本）"**：OCR/推断得到的页码是**候选**，不是结论。
6. **区分原文／转述／推算**：直引语给页码；转述只给线索并注明；推算值必须标出。
7. **报告与执行记录同步产出**：每轮留一份可复现记录（含命令与验收数字）。
8. **不删用户素材**：可以删库内记录；**删磁盘文件要先问**。

## 11. 路径与可移植性（`_paths.py` + 项目布局.json）

**问题**：`_toolkit` 下的脚本曾把 `<DSH_ROOT>\example-project\...` 直接写在模块级常量里（实测 94 行、约 70 个文件）。换机器、换盘符、改项目名就全废，而且失败方式常常是"库是空的"或"文件找不到"，看不出真正原因。

**机制**（`<REPO>/tools\_paths.py`，共享模块，**不是工具**、不进工具索引）：

| 层级 | 说明 |
| --- | --- |
| 解析优先级 | ① 命令行参数 → ② 环境变量（`KB_ROOT` / `LITDB_PROJECT` / `LITDB_LIT` / `LITDB_DBDIR` / `LITDB_PAPERS`）→ ③ **项目自己声明** `<项目根>\项目布局.json` → ④ 结构探测（唯一命中才用）→ ⑤ **报错，绝不猜** |
| 结构探测 | 按结构而非名字找：含 `.kb\kb.sqlite`（**非空**）或 `05_文献数据库` 的一级目录 = 项目根；`*/01_文献` = 素材目录 |
| 空壳库处理 | **0 文档的空壳库不算候选**。引擎在错误路径上会自动建空库，那种空库一旦落在探测范围内就会造成"多个候选 → 解析失败"。所以它既不是知识库，也不参与探测（`_paths.py --selftest` ⑤a 专门验证这条） |
| 项目布局.json | 项目根下的可选声明，例：`{"kb": ".kb", "db": "05_文献数据库", "lit": "topic-a/01_文献", "papers": "topic-b/03_论文"}`。**多个候选（如两个 `01_文献`）时靠它消歧**；`papers` 这类无结构约定的目录只能靠它或环境变量 |
| 诊断 | `python <REPO>/tools\_paths.py` 打印本机各逻辑路径的解析结果（未解析的会说明原因） |

**改了哪些**：**36 个可复用脚本**已改为调用 `_paths`（KB 读写线 + 页码/引文线），每个都留 `.bak-20260916-prePaths[2]` 备份。验证方式：全部 `py_compile` 通过 → 含 argparse 的跑 `--help` 通过 → **8 个只读脚本改造前后输出逐字节一致**（行为等价）。工具库口径"含硬编码路径"从 **87/137 降到 64/137**。

**没改的**：一次性调查脚本（`_p0_*`、`_probe_*`、`_layout_*`、`_litdb_*` 等）——它们本就是某次调查的快照，硬编码路径是它们的固有属性；换项目时应重写而不是参数化。

> **插入 import 的教训**：把 `from _paths import ...` 插在"首个用到替换结果的行之前"会插坏文件——若那一行在多行表达式（dict/list/跨行调用）内部，就直接语法错误（实测 `_diagnose_unmatched.py` 踩中）。**必须插在顶层 `import`/`from` 块之后。**

## 12. 升级与重灌（**先隔离演练，再动生产**）

引擎会提示"库是用旧修订写的，建议重灌"。**这件事不能照着提示做**——本项目的实测结论是：**重灌会静默摧毁页锚点线，但可以用两步回填完整救回。**

### 12.1 实测数据（2026-09-16 在隔离副本上做的演练，生产库全程只读）

| 阶段 | 文档 | 分块 | 向量 | 页锚点 | 覆盖率 | integrity |
| --- | --- | --- | --- | --- | --- | --- |
| 升级前（基准） | — | 100% | 100% | 100% | **97.0%** | ok |
| rev5 全量重灌后 | — | 100.4% | 100.7% | **23.5%** | **22.7%** | ok |
| 一步回填（按 `section`） | — | 100.4% | 100.7% | 98.1% | 94.7% | ok |
| **两步回填**（再按正文标记） | — | 100.4% | 100.7% | **100.8%** | **97.3%** | ok |

> 计数一律以**升级前基准 = 100%** 表示（文档数不变，故留「—」）。
> 绝对数字（文档数/块数/向量数）属于具体项目的过程数据，不在本仓库公开——
> **看结论只看比例即可**：页锚点掉到基准的 23.5%，两步回填回到 100.8%。

- 重灌 **19.6 分钟**（1 万块级；比"每千块 36 秒"的外推慢得多，因为 PDF/docx **解析**也占时间）；
- 形如「第 N 页」的小节（占全部块约七成），重灌后**全部变成 0 带锚点**；一步回填全部恢复；
- 逐文档按页号集合比对：**110 篇中完全一致 108 篇、缺页 0 篇**（另 2 篇"页更多"是因为新分块边界更宽，取的是文本里真实写着的页码）；
- 页号并集：基准 1,176｜两步回填后 1,176｜共有 1,176；
- **检索质量对照（自检索 20 条，同一查询打两个库）**：**位次完全一致 20/20**、Top-5 命中 17/20（两库相同）、首位平均分相同（0.033）、耗时相当（37 vs 38 ms）。
  两例页码差异已查明是"返回了不同的块"（基准返 Abstract 块、演练返 Body 块，**两边都带页码**），不是页码丢失。
  → **重灌的唯一可测影响是页锚点字段（可完整回填）；检索排序与命中率不变。**

### 12.2 原因（为什么新版引擎不再写页码字段）

文本素材的页码标记有两种形态：**小节名**（`#### 第 N 页`）与**正文标记**（`--- 第 N 页 ---`、`【页眉】…N`）。
在当前修订（rev5）上，前者只进 `chunks.section`、后者**留在正文里**，两者都**不再写入 `page_start`**；
而旧修订（库内标记为 `3.1.0/rev4`）会写。于是重灌后页码字段大面积为空——**不报错、不提示**。

### 12.3 标准动作（三步）

1. **隔离演练**（推荐）：把库复制到另一个目录，在副本上跑完整流程；生产库只读。演练脚本与结果见 `引擎升级演练报告_20260916.md`。
2. **用工具做升级**（顺序即安全措施）：
   ```
   python 03_工具\安全升级.py --kb "<项目>\.kb"                              # 只出计划
   python 03_工具\安全升级.py --kb "<项目>\.kb" --apply --offsite "<另一个盘>"  # 执行
   ```
   工具固定顺序：**量基准 → 强制备份 → 重灌 → 重量 → 锚点下降则自动两步回填 → 复核 → 出报告**；
   并会自动预警"本库的页锚点很可能来自文本页标记"（判据：页章节数 ≥ 锚点数的一半）。
   **重灌后还会自动回填元数据**（见 12.5）并清除"凭空写入"的年份。
3. **复核**：`锚点覆盖率 ≥ 升级前`、`integrity=ok`、悬空块/无向量块/盲文档 = 0、`indexed_with` 已是当前 rev，
   以及**元数据逐字段比对**（最容易漏的一项，见 12.5）。

### 12.5 重灌还会打坏"元数据"——比丢页码更隐蔽

`rebuild` 会**重跑 `extract_meta`**，于是人工逐篇核对或 Zotero 中继得到的 `title/authors/year/journal/doi`
会被"原始抽取结果"覆盖。**全文、分块、页码、检索全都正常**，所以极难察觉。

**实测后果**（2026-09-16 生产库 rev5 重灌，与升级前快照逐字段比对）：

| 字段 | 被改坏的文档数 | 典型形态 |
| --- | --- | --- |
| `authors` | **大部分文档** | 人名（张三、李四…）→ 空，或变成数据库站名（`<聚合站点域名>`、`<库商名>`） |
| `journal` | **多数文档** | 期刊名（刊名甲、刊名乙…）→ 空 |
| `title` | 4 / 114 | 多了 Markdown 的 `# ` 前缀 |
| `year` | 16 / 114 | 空 → **2026**（= 文件年份，引擎在无年份信号时会兜底取 PDF `creationDate`） |

**处置**：`安全升级.py` 已在重灌后自动执行「元数据回填 + 清除凭空年份」；
单独修复用 `恢复元数据.py`：

```
python 03_工具\恢复元数据.py --kb "<项目>\.kb" --from "<备份 kb.sqlite>"                        # 看计划
python 03_工具\恢复元数据.py --kb "<项目>\.kb" --from "<备份 kb.sqlite>" --apply --clear-suspect-years
```

它的规则（保守、不反向破坏）：备份有值且不同 → 回填；**备份为空、当前有值 → 保留**（不回退新得到的信息，如新抽到的 DOI），
但**若 `year` 等于文件年份（`docs.mtime` 的年份）→ 判为"凭空写入"，归 NULL**（判据用库内数据，可核对）。

> **验收门**：重灌后的元数据必须与升级前快照"**逐字段比对**"，差异逐条解释。本案例最终 111/114 篇完全一致，
> 余 3 篇差异已列明（其中 1 篇 authors 是数据库公司名）。

### 12.4 两条硬规则

- **不要绑 `chunk.id`**：重灌会重建全部编号。要绑就绑"文本内容 + 页码/时间码"。
- **不要在同一个库里"部分重灌"**：`rebuild` 是全库动作；要靠回填补齐，而不是留下半新半旧的库。

## 附录 A：本项目实测数字（**只是示例，不是规范**）

**以下数字一律取量级区间**——它们的作用是让你对"这套流程干完是什么规模"有个概念，
不是让你照抄。真实项目的精确数字（文档数、块数、各卷偏移量）属于研究过程数据，
**不应随代码一起公开**，本仓库因此不列。

| 维度 | 量级 |
| --- | --- |
| 知识库 | 文档数以百计；块数万级；**向量数 ≈ 块数**（据库内实算） |
| 页锚点覆盖 | `page_start` 覆盖率**高于九成**（不是 100%，缺口要能解释） |
| 页章节 | `section` 形如"第 N 页"的块占比很高——这是"引文可回查"的直接体现 |
| 元数据填充 | authors / year / journal 大多在七八成以上；**`doi` 常年是个位数百分比**（扫描件没有 DOI，别指望）；`zotero_key` 可能为 0 |
| 单卷 OCR | 一卷数百页、百万字符级、**数小时**（取决于机器与版式） |
| 页码偏移 | **各卷不同**（实测落在 +7 ～ +13 之间）；**必须逐卷自证，不能照抄** |
| 引文工作 | 页码回填数十处；逐字校勘数十条；**几乎必然出现 1–2 处实质讹误或文本归属错误**——这正是设"校勘"与"交叉验证"两步的原因 |
| 引擎 | 嵌入用 `BAAI/bge-small-zh-v1.5`、重排用 `bge-reranker-base` 这一档的小模型即可 |
| 守卫自测 | `_kb_guard.py --selftest` 应全绿；不绿就不要写库 |

**产物后缀**（印证 §3 规范）：`.pdf`｜`.docx`｜`.PAGES.md`｜`.OCR.md`｜`.full.md`｜`.OCR.docx`｜`.OCR.layout.json`｜`.OCR.quality.md`。
后三项**只有新版式感知 OCR 才产出**——旧产物没有。**规范要求 ≠ 现状已达标**。

## 一句话

> **数据库的可靠性不取决于向量模型有多强，而取决于"页码这条线"有没有从扫描页一路贯通到论文标注。**
> 这一路上最危险的不是"读不出来"，而是"读错但看起来对"——所以每一步都要留下依据，留空胜过猜测，写完立刻校验。
