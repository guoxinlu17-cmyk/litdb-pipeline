# litdb-pipeline · 页码锚定的文献库构建流水线

把**扫描件 / PDF / Word** 建成一个"全文可检索、**引文能落回印刷页码**"的文献库，
并把引文定位、交叉验证、逐字校勘、页码回填做成可复核的流程。

面向需要「引文回查纸本」的研究项目：书籍、期刊论文、档案扫描件、docx 文稿。

---

## 两条不变式（整条流水线的判据）

> **不变式 1：页码是主线。**
> 从扫描页开始，页码就要落进文本标记，一路贯通到入库后的 `section` / `page_start`，
> 再到论文里的引文标注。**这条线一断，后面全是猜**——检索能返回文本，但你无法回答
> "这句话在原书第几页"。

> **不变式 2：宁可留空，不可猜测。**
> 最危险的不是"读不出来"，而是"**读错但看起来对**"。所以：读不出来 → 如实记 `status`；
> 推不出页码 → 留 `NULL`；没核实 → 标"待回查纸本"。

这两个不变式能解释下面几乎所有的设计选择。若你的项目不需要"引文可回查纸本"，
可以砍掉阶段 2、5，但**不要**用"承前/承后"之类的兜底去伪造页码。

---

## 五层架构

```
L1 素材层    原始 PDF / DOCX / 扫描件 / 已有 Markdown
                 ↓  体检：页数、有无文字层、版式类型
L2 文本化层  三条并行路线，按素材类型择一（可混用）
                 ① 版式感知 OCR        ← 无文字层的扫描件
                 ② docx 页眉法（免OCR） ← "一页一节"且页眉带页码的 docx
                 ③ OCR 文本转印刷页码   ← 已有 OCR，但页码是 PDF 页序
                 ↓  产出：逐页文本 + 页标记 + 质量报告
L3 结构层    分块 + 页码字段 + 向量      ← 由知识库引擎完成
                 ↓
L4 应用层    检索 / 引文定位 / 逐字校勘 / 页码回填 / 二级文献抽取
                 ↓
L5 治理层    结构核查 / 去重 / 元数据修复 / 备份与回滚
```

**设计要点**：页码在 **L2 就要落进文本**（作为 `#### 第 N 页` 之类的页标记），
不要留到 L3 之后再补。切块器会把页标记抽成 `chunks.section`，检索结果直接可见、
可用 `filters` 精确取某页——这是"引文可回查"的实现方式。

本项目**自己写的是 L1/L2 与 L4/L5 的工具**；L3（入库、向量检索）走外部引擎，见下。

## 环境要求

### 1. 知识库引擎（必需）

L3 的入库与检索**不是本项目实现的**。本流水线通过一个 JSON-over-stdin 协议驱动
**DSH（DeepSeek Harness）的知识库插件 `dsh-kb-rag`**：

- 引擎文件：`<DSH profile>/node_modules/dsh-kb-rag/kb_engine.py`
- 对话侧工具：`kb_ingest` / `kb_search` / `kb_stats` / `kb_rag` / `kb_dedup` / `kb_fetch`
- **保底通道**：插件失效时用 `tools/kb_cli.py` 直接命令行驱动（`stats` / `ingest` / `search` / `rag`）

> 引擎位置可用 `--engine` 参数或 `KB_ENGINE` 环境变量指定。
> 没有 DSH 也可以只跑 L1/L2（体检、OCR、页码标定）——这部分不依赖引擎。

### 2. Python 依赖

| 包 | 用途 | 谁需要 |
| --- | --- | --- |
| `PyMuPDF` (`pymupdf` / `fitz`) | PDF 渲染与文本抽取 | OCR 与体检线 |
| `rapidocr_onnxruntime` | 版式感知 OCR | 路线① |
| `numpy` | OCR 图像处理 | 路线① |
| `Pillow` (`PIL`) | 图像处理 | 路线① |
| `python-docx` (`docx`) | docx 解析 | 路线②、md2docx |

```bash
pip install pymupdf rapidocr_onnxruntime numpy pillow python-docx
```

只用路线②（docx 页眉法）与核查/治理线的话，`python-docx` 之外基本不需要。

## 快速开始

### 第 0 步：先配置项目（**别跳过**）

工具必须知道你的素材、题录库、论文各在哪。三种给法，任选其一：

```bash
# 方式 A（推荐）：在项目根放一个 项目布局.json
cp 项目布局.json.example <你的项目根>/项目布局.json
# 然后改里面的路径

# 方式 B：环境变量
setx LITDB_PROJECT "<你的项目根>"
setx KB_ROOT       "<你的项目根>\.kb"

# 方式 C：每次命令行传参（各工具的 --kb-root / --project）
```

先验证解析对不对：

```bash
python tools/_paths.py        # 打印每个逻辑路径解析到什么；没解析出的会说明原因
```

> ⚠️ **不配置就跑工具会报 `PathError`**，部分工具连 `--help` 都会报（见「已知限制」）。
> 这是刻意的：**宁可报错，不要猜路径**。

### 第 1 步：确认工具箱本身是好的

```bash
python run_selftests.py
```

它会在临时目录搭一个最小项目骨架再跑自测，因此**与你的项目长什么样解耦**。
8 个工具全绿才开始干活；不绿先解决环境。

### 第 2 步：按 SOP 走

**动手前读一遍** [`docs/SOP.md`](docs/SOP.md)（十二步流程、工具总表、失败模式、检查清单、速查命令）。
本 README 只给骨架。

## 已知限制

1. **44 个工具里有 25 个在 import 阶段就解析路径**，所以没配置项目时连 `--help` 都会抛
   `PathError`（实测：`--help` 可用 19 个／被挡住 25 个）。
   这是"宁可报错不要猜"的直接后果。**先按「快速开始·第 0 步」配置好即可。**
   （没改造成惰性解析，是因为那要动 25 个文件的模块级常量，风险大于收益。）

2. **工具大多绑定项目结构**，不是拿来即用的通用件。复用 = 复用流程与思路 +
   按需参数化脚本。分级依据见 `docs/SOP.md` §5。

3. **页码偏移量因卷而异**，必须逐卷自证（判据：命中页文本里真的印着推算出的页码，
   且差值成片而非散点）。**不要照抄任何示例里的偏移值。**

4. **引文校勘几乎必然发现错误。** 实测会出现 1–2 处实质讹误或文本归属错误——
   这正是设"逐字校勘"与"交叉验证"两步的原因，不是流程没做好。

5. **重灌会静默摧毁页锚点。** 引擎提示"库是用旧修订写的，建议重灌"时**不要照着做**：
   实测页锚点覆盖率会从约 97% 掉到约 23%，需要两步回填才能救回（可回到约 97%）。
   标准动作与实测数据见 `docs/SOP.md` §12。

## 数据与隐私

**本仓库只含流程与工具，不含任何文献内容或研究数据。**

- 文档里的 `示例文集` / `示例人物` / `topic-a` 等是**占位符**，用于替代原始项目的
  专名、篇名与卷次。
- 代码里的"引文 + 页码"用例已全部外置为**外部 JSON**（`*_cases.json`），
  仓库不内置任何真实引文。
- 实测数字（文档数、块数、卷数、各卷偏移量）一律改为量级区间。

**你自己使用时请注意**：

- `.gitignore` 已排除 `.kb/`、素材目录、题录库 CSV 与论文稿——**别把它们提交上去**。
  扫描件与 OCR 文本常涉及版权；未发表论文与访谈稿涉及隐私。
- **访谈材料必须在入库之前脱敏**：检索片段会进云端模型的 prompt，
  用了这套工具就不是"本地封闭处理"了。`_interview_check.py` 会检出手机号/邮箱并给出警告。
